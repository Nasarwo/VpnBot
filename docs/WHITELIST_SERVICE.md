# Услуга «Обход белых списков» — реализация и порядок внедрения

Состояние на 4 октября 2026, приёмка — 5 октября 2026 (`docs/WHITELIST_ACCEPTANCE.md`).
Реализация локальная, проверена тестами и на изолированных реальных 3x-ui/SubHub; в
production не применялась. Применение выполняется по отдельному указанию владельца.

## 1. Что получает пользователь

- В существующей подписке SubHub появляется отдельный конфиг «Обход белых списков».
  Отдельная ссылка не выдаётся. Обычные конфиги остаются безлимитными.
- Бесплатный пакет: 10 ГБ при каждой подтверждённой оплате подписки (замена остатка,
  а не прибавление; оплата на 180 дней — один пакет), 3 ГБ однократно за trial.
  Ежемесячного начисления нет.
- Бессрочный VPN-доступ (`expires_at IS NULL` + привязка + `is_active`) — безлимит;
  роль администратора на это не влияет.
- Покупка пакетов (10 ГБ — 49 ₽, 25 ГБ — 99 ₽, 50 ГБ — 199 ₽) по квитанции и
  подтверждению администратором; только при активной подписке. Купленное не сгорает.
- Конфиг работает только при активном доступе и положительном остатке. Исчерпание
  останавливает только этот конфиг. Покупка при активной подписке возобновляет его.

Раздел в боте: главное меню / «Моя подписка» → «Обход белых списков». Показываются
статус, срок подписки, бесплатный и купленный остатки, пакеты, отложенное применение
и устаревшие данные при недоступной панели.

## 3. Модель учёта

**Состояние** (`whitelist_accounts`, одна строка на пользователя):
`free_bytes`, `paid_bytes` — остатки на момент контрольной точки
`usage_checkpoint_bytes` (накопленный `up+down` клиента панели), `server_id` и
`traffic_row_id` (ключ строки `client_traffics`) — к какой эпохе счётчика относится точка.
`usage_observed_bytes`/`usage_observed_at` (миграция `f3a4b5c6d7e8`) — последнее
прочитанное значение счётчика текущей эпохи и момент, не раньше которого оно прочитано.
Они обновляются при каждом чтении, в том числе когда остатки не сверяются (событие ждёт
решения), и служат для обнаружения сброса и отбраковки устаревших пакетных чтений.

**Списание** нового расхода Δ = счётчик − точка:

```text
free'  = max(0, free − Δ)
paid_used = max(0, Δ − free)
paid'  = max(0, paid − paid_used)
checkpoint = счётчик            # учтённый расход повторно не списывается
```

**Квота панели** — абсолютная: `totalGB = checkpoint + free + paid`; при нулевом
остатке `enable=false`, `totalGB = max(checkpoint, 1)`. После сброса счётчика при
нерешённом событии точка может быть отрицательной (см. «Сброс/пересоздание клиента»):
тогда `totalGB = остаток + checkpoint`, а при неположительном значении клиент
выключается с `totalGB = 1`. Для бессрочного доступа
`totalGB=0, expiryTime=0`. Повтор применения выставляет то же значение — объём не
прибавляется на retry. `expiryTime` = срок подписки; истёкшая подписка → `enable=false`.

**Журнал** (`whitelist_ledger`): каждая выдача/начисление — строка с уникальным
`source_key`: `payment:<id>` (бесплатный пакет за оплату или покупка трафика),
`trial:<user>`, `rollout:<user>`. Также записываются `usage_rebase` (сброс счётчика) и
`adjust` (ручная корректировка). Повторное подтверждение, retry, рестарт и повтор
очереди не создают второй строки.

**Упорядоченные события учёта** (миграция `d1e2f3a4b5c6`). Выдача пакета
(`free_set` — бесплатный остаток := объём) и покупка (`paid_delta` — купленный +=
объём) — события журнала в порядке `id`. Событие меняет подтверждённые остатки
только вместе с расходом до него, поэтому ему нужна привязка `anchor_bytes` —
значение счётчика в момент события:

| Состояние | Когда | Остатки `whitelist_accounts` |
|---|---|---|
| `settled` | расход до события известен | событие применено после списания расхода до привязки |
| `pending` | статистика недоступна (ошибка чтения, сервер выключен, клиент не найден на панели) | не меняются; событие и оплата сохранены |
| `uncertain` | сверка не может определить, был расход до или после события | не меняются; границы `anchor_min_bytes..anchor_max_bytes`, нужно решение администратора |

Событие применяется сразу, если чтение в этой же операции прошло и неприменённых
событий нет, либо у клиента нет точки отсчёта (клиента панели ещё нет — расхода
нет). Иначе оно `pending`. Ближайшее успешное чтение (очередь, фоновая сверка,
просмотр баланса, следующая операция пользователя) применяет события строго по
порядку и привязывает каждое:

1. счётчик не изменился с прошлой точки — расход 0, порядок не важен;
2. `last_online + 1 мин ≤ время события` — после события панель трафика не видела,
   весь расход был **до** события (минута — допуск на расхождение часов);
3. покупка, если расход не больше остатка до неё — итог не зависит от порядка;
4. иначе событие становится `uncertain`: неразделённый расход **не списывается**
   ни с одного остатка, следующие события ждут (`pending`, с точной привязкой,
   если они записаны при доступной статистике).

Контрольный пример: подтверждено 2 + 15, до продления израсходовано 5, при оплате
статистика недоступна. Оплата сохраняется (`CONFIRMED`/`APPLIED`), событие —
`pending`, остатки остаются 2 + 15. После восстановления `last_online` раньше
оплаты → 5 списываются со старых остатков (0 + 12), затем пакет: **10 + 12**.

Пока есть неприменённые события, панели задаётся **нижняя граница** квоты:
`totalGB = checkpoint + остатки с событиями без неучтённого расхода` (в примере
0 + 10 + 15). Панель сама списывает с неё весь расход после точки; при любом
разделении фактический остаток не меньше. Пользователь видит подтверждённые
остатки с датой и список ещё не учтённых начислений, а не устаревшее значение
под видом текущего.

**Решение неопределённости** (`/wl <tg>` показывает оба варианта на конец
периода): `/wlresolve <tg> до|после <причина>` относит неразделённый расход до или
после первого `uncertain` события, применяет его и продолжает сверку по порядку;
`/wladjust <tg> <бесплатно> <куплено> <причина>` задаёт оба остатка на текущий
счётчик и закрывает все неприменённые события. Корректировка требует успешного
чтения счётчика, если клиент на панели существует. Оба действия — в аудите.

**Применение** отделено от начисления: `desired_version` растёт при любом изменении
намерения (выдача, покупка, срок, блокировка); `applied_version` фиксируется после
read-after-write проверки панели (`totalGB`, `expiryTime`, `enable`, inbound, flow цели).
Размещение клиента (целевой inbound и flow) подтверждается отдельно — см. «Смена
целевого inbound и перенос клиентов». Фоновая
очередь с backoff (1 мин → 1 ч) применяет **текущее** состояние БД, поэтому старая задача
не может уменьшить срок, потерять покупку, восстановить старый пакет или включить
истёкшую подписку.

**Статус заявки на покупку трафика** (миграция `e2f3a4b5c6d7`). Ожидание применения
хранится не в тексте `payment_requests.last_error`, а в `apply_pending_version` —
версии `desired_version` учёта, с которой начисление попадает на панель. Поле
ставится в той же транзакции, что и начисление (`APPLIED` + событие), поэтому сбой
между commit и обращением к панели не делает заявку «применённой». Ожидание снимается
(`release_applied_credits`, после каждой синхронизации и сверки расхода) только когда
выполнены оба условия: `applied_version >= apply_pending_version` и событие журнала
`payment:<id>` сверено (`settled`). Следствия:

- несколько покупок оцениваются независимо: более поздняя покупка или любое
  изменение баланса поднимает `desired_version`, но уже применённую заявку снова
  ожидающей не делает; старый повтор не снимает ожидание с более новой заявки;
- повтор подтверждения/retry уже начисленной заявки ничего не начисляет и ожидание
  не ставит; при успешном применении он снимет его;
- применение квоты при несверенном расходе (`pending`/`uncertain`) заявку не
  освобождает — она ждёт сверки, как и «ожидает» в разделе пользователя;
- `last_error` заявки остаётся для реальных ошибок и снятием ожидания не
  затрагивается. Подписки (`kind=subscription`) модель не меняет.

Статус показывают `texts.payment_status_label` («трафик начислен, ожидается применение
на сервере» ↔ «трафик начислен»), карточка и история заявок администратора.
Раздел пользователя о заявке не сообщает: он берёт «Оплата сохранена» из учёта
(`desired_version`/`last_error` аккаунта), поэтому тоже исчезает после применения.

**Сброс/пересоздание клиента на панели** (счётчик меньше последнего прочитанного
значения или сменился `traffic_row_id`). Проверка выполняется при каждом чтении — в
сверке, очереди, просмотре баланса, операции пользователя — **до** обработки событий,
в том числе пока событие ждёт решения администратора (`uncertain`). Последнее чтение —
`usage_observed_bytes`; для учёта, ещё не читавшегося после миграции `f3a4b5c6d7e8`, —
наибольшее из точки и границ/привязок неприменённых событий.

Новая эпоха продолжает последнее прочитанное значение прежней `L`: точка и привязки
неприменённых событий (`anchor_bytes`, границы `uncertain`) уменьшаются на `L` и дальше
сравниваются только со счётчиком новой эпохи. Следствия:

- прежняя база не становится доступным трафиком; квота новой эпохи равна доступному
  объёму на момент последнего чтения;
- расход прежней эпохи, ещё не списанный с остатков (`L − точка`, например
  неразделённый период `uncertain`), остаётся вычтенным из квоты: точка становится
  отрицательной, `totalGB = остаток с событиями + точка`. В карточке `/wl` это строка
  «После сброса счётчика с остатков ещё не списан расход прежней эпохи …»;
- остатки, оплаченные начисления и журнал не меняются; пишутся `conflict` и строка
  `usage_rebase` (последнее чтение, новое значение, строки статистики, не списанный
  расход прежней эпохи); к пересчитанным событиям добавляется примечание;
- `/wlresolve` после сброса применяет выбранный вариант к прочитанному периоду
  прежней эпохи, затем списывает весь последующий расход, включая расход новой эпохи;
  `/wladjust` задаёт остатки на текущий счётчик новой эпохи. До решения квота остаётся
  нижней границей (не больше меньшего из вариантов), покупки после сброса сразу
  увеличивают квоту и применяются по порядку после решения;
- без неприменённых событий (обычный случай) `L` совпадает с точкой: новая эпоха
  начинается с нуля, списывается только её расход, ожидающие события привязываются к
  ней по тем же правилам; если расход новой эпохи нельзя разделить, событие становится
  `uncertain`.

Расход между последним чтением и сбросом неизвестен и не списывается — это явно
показано в расхождении. Пакетное чтение, начатое раньше сохранённого чтения той же
учётной записи (`usage_observed_at`, момент не раньше фактического чтения), не
применяется (BUSY, повтор в конце обхода) и не принимается за сброс.

Если клиент удалён вместе с подпиской или сменился сервер/идентичность до сверки,
счётчик утрачен: ожидающие события становятся `uncertain` без верхней границы, а у
уже неопределённого события снимается верхняя граница прочитанного периода и
привязки — его значения несравнимы со счётчиком нового клиента. Решение — только
`/wladjust`.

**Ручное отключение**: блокировка администратором в боте (`admin_blocked`) и
обнаруженное отключение клиента на панели (панель выключила подтверждённо включённого
клиента без исчерпания и истечения) сохраняются; чтение баланса и фоновые повторы не
включают клиента. Выключенный сервер услуги вообще не изменяется.
Явная разблокировка администратором (`set_admin_block(False)`) — единственное, что снимает
блокировку. Она сбрасывает `applied_enable`: подтверждение «клиент включён» устарело, пока
решение не применено, поэтому чтение баланса и фоновый повтор не определяют ещё не
снятое ручное отключение заново. `applied_enable` фиксируется следующим успешным применением.
Разблокировка не обходит срок и остаток: `compute_target` по-прежнему оставляет клиента
выключенным при истёкшей подписке или исчерпанной квоте (бессрочный доступ включается).

Последовательность событий оплаты подписки: блокировка пользователя → сверка расхода с
панелью → событие выдачи (применённое или `pending`) и target **в одной транзакции** →
обычные панели → whitelist-панель. Покупка: сверка → событие начисления и `APPLIED` в
одной транзакции → панель. Недоступная статистика не мешает сохранению оплаты; сверка
расхода и применение квоты ждут очередь.

### Смена целевого inbound и перенос клиентов (2026-10-06)

Источник — P1 повторного ревью (`docs/REVIEW_2026-10-06.md`): после выбора нового
inbound сервер получал статус «готов», а очередь выбирала только учёты с
`desired_version > applied_version` — синхронизированные клиенты оставались на прежнем
inbound; фоновая сверка размещение не сравнивала. После удаления прежнего inbound
пользователи теряли конфиг услуги до отдельной операции.

**Модель.** Размещение — такое же целевое состояние БД, как квота:

| Где | Что хранится |
|---|---|
| `server_inbounds` (единственная включённая строка whitelist-сервера) | текущая цель и её flow (`flow` NULL — без flow) |
| `whitelist_accounts.placement_server_id/inbound_id/flow/at` | **подтверждённое** размещение: чтением подтверждены привязка к цели с её flow и снятие прежних привязок услуги. NULL — не подтверждалось |
| `whitelist_placements` | привязки, созданные **услугой**: `attaching` (записано до запроса attach/create), `attached` (подтверждено чтением), `detaching` (прежняя цель, снимается); `origin` — `service` или `claimed` (`/wlclaim`) |

**Обнаружение.** Очередь (`process_due`) выбирает, кроме изменений учёта, учёты с
клиентом на панели (`panel_email`), у которых подтверждённое размещение не равно
текущей цели (сервер, inbound, flow) или есть строки услуги, кроме подтверждённой
привязки к цели. Это условие на сохранённом состоянии, а не пометка в момент смены,
поэтому одинаково срабатывает при выборе inbound в разделе услуги, при сверке реестра
(прежний inbound удалён на панели и целью стал единственный оставшийся), после
`/addinbound`/`/delinbound`/`/clearinbounds` (они снимают готовность сервера до
«Синхронизировать сервер», т. е. до проверки совместимости новой цели/flow с SubHub),
при замене сервера услуги и после рестарта. Продление или покупка не нужны.
Синхронизированные учёты истёкших, заблокированных и бессрочных пользователей
переносятся так же: срок, `enable` и блокировка задаются из БД, перенос их не меняет.

**Порядок одного применения** (`_push`, под блокировкой пользователя):

1. Чтение клиента (оно же сверка расхода). Если цели среди привязок нет, строка
   `attaching` записывается и **сохраняется (commit) до запроса**.
2. `apply_quota_client`: attach недостающей цели → `clients/update` прочих привязок с их
   собственным flow → `clients/update` цели с её явным flow → чтение: квота, срок,
   enable, привязка к цели и flow клиента в `inbounds/get/{цель}`.
3. Привязка к цели: `attached` (услуги) — если строка уже была или этот вызов сам
   прочитал отсутствие и прикрепил; иначе это чужая/прежняя привязка, строки нет.
   Сверка прочитанного счётчика и при изменении квоты — повторная запись (как раньше).
   Квота считается применённой (`applied_version`).
4. Привязки услуги к прежним целям: отсутствующие на панели строки удаляются; к
   присутствующим — `detaching`, **commit**, затем `detach` и чтение: привязок не осталось.
   Чтение после detach снова сверяет счётчик (смена строки статистики → новая эпоха,
   квота пересчитывается — доступный объём не растёт).
5. Итог: цель есть среди привязок, привязок услуги к прежним целям нет → `placement_*`
   = цель. Только здесь перенос считается завершённым.

Любой сбой (недоступная цель, ошибка attach/update/detach, неподтверждённое чтение)
сохраняет `last_error` и backoff 1 мин → 1 ч (`next_sync_at`); прежняя привязка не
снимается, пока новая не подтверждена. Точки восстановления после рестарта:

| Прервано | Что в БД | Следующий проход |
|---|---|---|
| после записи `attaching`, до/после attach | строка `attaching`, прежнее `placement_*` | цель на панели есть → привязка услуги (attach запрошен после чтения «нет»); нет → attach заново |
| после подтверждения квоты, до/после detach | цель `attached`, прежние `detaching`, квота применена | привязки нет → строка удаляется; есть → detach заново |
| после detach, до commit | то же | привязки нет → итог подтверждается без повторного detach |

**Новая цель во время незавершённого переноса (7→8→9).** Применяется всегда текущая
цель из БД; строки услуги к 7 и 8 — прежние цели, их снимет ближайший проход после
подтверждения 9. Backoff прежней неудачной попытки сохраняется и для новой цели;
устаревший повтор не прикрепляет клиента к 8. Повторный выбор той же цели ничего не
меняет (очередь пуста, запросов к панели нет).

**Чужие привязки.** Привязка без строки услуги (администратор прикрепил клиента к
другому inbound'у этой панели, или привязка была до учёта привязок) не снимается и
расхождением не считается. Учёты, перенесённые до миграции `a4b5c6d7e8f9`, не имеют ни
`placement_*`, ни строк: очередь один раз проверяет их размещение (attach к цели при
отсутствии, явный flow), но прежнюю привязку неизвестного происхождения своей не
объявляет. Если администратор знает, что inbound был целью услуги, `/wlclaim
<inbound_id> <причина>` создаёт строки `claimed` для учётов сервера (в аудите), и
перенос снимает такие привязки. Текущую цель признать нельзя.

**Что сохраняется.** attach копирует общую запись клиента (UUID/пароль/auth, email,
subId, Telegram ID, срок, квота), update — read-modify-write с прежними секретами и
дополнительными полями; detach не трогает строку статистики. Остатки, журнал,
открытые (`pending`/`uncertain`) события, их привязки, `usage_observed_*`,
отрицательная точка, блокировка и срок переносом не меняются; пакет не выдаётся.
Квота после переноса — та же абсолютная `totalGB`, расход продолжает списываться по
тому же счётчику. Если панель всё же пересоздаст строку статистики, это обнаруживается
как новая эпоха (как внешний сброс) и квота пересчитывается от остатка.

**flow.** flow цели задаётся явно: значение `server_inbounds.flow` записывается в
привязку к цели, а при его снятии — очищается (раньше бот только дополнял пустой flow и
никогда не менял заданный). Смена flow на текущей цели — такой же перенос (расхождение
`placement_flow`). Прочие привязки обновляются своими запросами со своим flow,
прочитанным из `inbounds/list`; цель обновляется последней. Следствия по версиям:

- 3.3–3.9: flow прежней цели во время сосуществования и flow чужих привязок не меняются;
- **3.2.0**: фильтра нет, flow — фактически свойство общей записи: последний update
  записывает flow цели во все привязки. Во время сосуществования прежняя цель получает
  flow новой, чужая привязка — тоже; бот видит это при чтении и пишет предупреждение в
  журнал, но предотвратить не может.

**Доступ во время переноса не гарантируется.** Новая цель — другой inbound (порт,
параметры REALITY, транспорт): устройство пользователя получает новую ссылку только
после синхронизации SubHub (бот запрашивает её после прохода, в котором что-то
применено) и обновления подписки в приложении. Старая ссылка работает, пока привязка к
прежнему inbound'у не снята, — обычно секунды после подтверждения новой; если flow
прежней привязки изменился (3.2.0), старая ссылка с прежним flow может перестать
подключаться ещё раньше. Переходный период без интервала ожидания перед detach не
предусмотрен.

**D-3 и detach.** В 3.9.0 снятие привязки включённого клиента ставит перезапуск Xray
(`restartXrayOnClientDisable=true`, по умолчанию; cron 30 с), а перезапуск Xray теряет
учёт трафика ≈ 5 с у **всех** клиентов панели (D-3, протокол
`docs/acceptance/xui_traffic_d3_2026-10-06.md`, сценарий S3). Перезапуски от снятий в
пределах 30 с объединяются, но массовый перенос (очередь — до 50 учётов за проход
каждые 30 с) даёт серию перезапусков на время переноса. Перенос эту потерю не
устраняет и не компенсирует: менять цель — в часы наименьшего трафика (§6, шаг 10).
Поведение detach в 3.9.0 установлено по исходникам, на стенде не измерялось.

**Фоновая сверка** сравнивает и размещение: целевая привязка, flow клиента в
настройках цели (список inbound'ов читается один раз на пачку) и отсутствие привязок
услуги к прежним целям. При расхождении подтверждение (`placement_*`) снимается, и учёт
попадает в очередь; `desired_version` и backoff незавершённого переноса не трогаются.

**Администратору.** Раздел услуги: «Размещение на inbound N (flow: …): подтверждено X
из Y; ожидает Z; ошибка E» и, пока перенос не завершён, напоминание, что готовность
сервера не означает перенос клиентов; число ещё не снятых привязок услуги. `/wl`:
подтверждённое размещение, цель, строки привязок с состоянием, последняя ошибка. После
выбора цели/синхронизации обработчик сразу выполняет одну порцию очереди и, если что-то
применено, запрашивает синхронизацию SubHub; дальше — worker очереди (тоже с SubHub).
`ops/whitelist_check.py`: `placement_mismatch` (фактическое расхождение на панели) и
`placement_pending` (перенос не подтверждён).

### Совместимость inbound с SubHub (2026-10-05)

Импорт строки inbound — ещё не готовность. Сверка (`sync_inventory`: при добавлении
сервера, «Синхронизировать сервер», `/import` и после выбора цели) проверяет целевой
inbound по данным `inbounds/list` теми же правилами, по которым SubHub строит ссылку
(`SingleLinkVpn/subhub/app/link_builder.py: build_link`, `mihomo_profiles._proxy`).
Совместимы только:

| Протокол / security / транспорт | Обязательные параметры inbound |
|---|---|
| VLESS + REALITY + `tcp`/`raw` (header `none`) | публичный ключ (`realitySettings.settings.publicKey` или выводимый `privateKey`), непустой `serverNames`, непустое значение в `shortIds`, `decryption=none` |
| VLESS + REALITY + `xhttp` | то же; flow не задаётся |
| Hysteria2 (`hysteria`/`hysteria2`) + TLS | — (SNI: `tlsSettings.serverName`, иначе `public_host` SubHub); проверено только по исходникам, не трафиком |

Несовместимы (сервер получает статус `incompatible`, «Сервер не готов: SubHub не
построит ссылку…», с перечнем причин): VLESS без REALITY (`none`, `tls`), VMess,
Trojan, Shadowsocks; VLESS REALITY через `grpc`/`ws` и с `header` ≠ `none` (SubHub
строит ссылку без `serviceName`/`headerType`); VLESS Encryption (`decryption` ≠ `none`,
SubHub передаёт `encryption=none`); отсутствие любого обязательного параметра.

Пока статус не `ready`, выдача, очередь и сверка не обращаются к панели услуги
(`server_ready`). Повторная настройка: исправить inbound в панели и нажать
«Синхронизировать сервер» — цель прежняя, сервер станет готов; при статусе
`incompatible` раздел услуги также показывает кнопки выбора другого inbound. Выбор
цели (`choose_inbound`) сам готовность не ставит: за ним сразу идёт сверка с панелью.
Сохранены: автоматическая первичная синхронизация, выбор одной цели при нескольких
inbound (кандидаты перечислены с пометкой «совместим/несовместим»), ручные
отключения, повторяемость, отсутствие выдачи пакетов при синхронизации.

**flow.** Бот не угадывает flow и не копирует настройки чужих клиентов. Клиенты услуги
получают flow только из явно заданного `server_inbounds.flow` целевой строки
(`/delinbound` + `/addinbound <server> <inbound> vless xtls-rprx-vision`); повторная
сверка его сохраняет, он попадает в объект клиента и в ссылку SubHub (только TCP/RAW).
Без него клиенты создаются без flow — так REALITY TCP проверен трафиком при приёмке.
Сверка сообщает администратору, какой flow задан, а если у существующих клиентов
inbound на панели есть flow — сколько их и с каким значением (без UUID, email, subId).
flow для `xhttp`/Hysteria2 или неизвестное значение — несовместимость.

**Граница проверки.** Совместимость — свойство данных панели. Она не доказывает, что
панель добавлена в `config.yaml` рабочего SubHub, что SubHub её успешно опрашивает,
что `reality_overrides`/`exclude_inbounds` SubHub не меняют результат, что порт и
`public_host` доступны клиентам. Сообщение «готов» об этом напоминает; шаг 5 runbook
обязателен.

Whitelist-клиент не получает `ClientServerMapping`: так он не влияет на признак
бессрочного доступа, антишеринг, mapping-путь продления и выбор идентичности. Его
идентичность (email/subId/UUID) берётся из существующей привязки подписки, поэтому
SubHub (`token_strategy: by_email`) включает конфиг в ту же ссылку.

## 5. Конкуренция и восстановление

- Все изменения остатков, оплаты, trial, покупки, очередь и выдача идут под
  `user_operation` (PostgreSQL advisory lock на отдельном соединении + локальный
  asyncio.Lock). Row lock заявки берётся уже внутри advisory lock; строки учёта не
  блокируются `FOR UPDATE` — сериализация по пользователю уже гарантирована, а
  `version_id_col` превращает невозможную гонку в ошибку вместо потери обновления.
- Durable intent: событие выдачи пакета фиксируется вместе с target оплаты
  (`CONFIRMED`); событие покупки — вместе с `APPLIED`. Рестарт после commit продолжает
  `recover_confirmed_payments` / очередь без повторного начисления; несверенное событие
  остаётся `pending` в БД и сверяется при первом успешном чтении.
- Фоновая сверка читает панель пачкой без блокировки и применяет результат только если
  чтение новее последней сверки (иначе устаревшее значение было бы принято за сброс)
  и ни одно неприменённое событие не создано после начала чтения (значение могло быть
  прочитано до события и не может быть его привязкой).

### Фоновая сверка расхода: обход, гарантии, ограничения

`reconcile_cycle` (отдельная задача `_whitelist_reconcile_poller`, не зависит от
`SERVER_HEALTH_POLL_SECONDS`) обходит **все** учёты активного whitelist-сервера:

- **Пачки и пагинация.** Учёты берутся по возрастанию `whitelist_accounts.id`
  (`id > курсор`), пачками по `WHITELIST_RECONCILE_BATCH_SIZE` (100); между пачками
  пауза `WHITELIST_RECONCILE_BATCH_PAUSE_SECONDS` (1 с). Курсор — id, а не
  `last_synced_at`: учёты без клиента на панели или с пропущенной сверкой метку не
  обновляют и раньше снова попадали в начало выборки, вытесняя остальных.
  Добавленные во время обхода учёты получают больший id и попадают в него; удалённые
  не выбираются.
- **Нагрузка на панель.** Одна сессия панели на пачку, чтение клиентов последовательное,
  пачки — с паузой. Оценка длительности: `N × (чтение + БД) + ⌈N/пачка⌉ × пауза`;
  например, 1000 учётов при 0,2 с на клиента — порядка 3,5 минут (расчёт, не замер).
- **Устаревшие чтения и сериализация.** Для каждой пачки фиксируется `read_at`; учёт
  применяется под `user_operation` теми же проверками (чтение новее последней сверки,
  нет события, созданного после начала чтения, тот же сервер и `panel_email`).
  Учёт, изменившийся между чтением и сверкой (продление, покупка, другая сверка),
  не применяется по устаревшему чтению и один раз перечитывается в конце обхода.
  Если повторная пачка не прочиталась, её учёты — **ошибки**; если они снова заняты
  (без ошибки HTTP) — «изменились»; в обоих случаях они не сверены.
- **Ошибки.** Ошибка чтения или сверки одного учёта считается ошибкой этого обхода,
  остальные обрабатываются. Если в двух пачках подряд не прочитался ни один клиент
  (панель недоступна), обход прерывается; следующий запуск (через минуту)
  продолжает с курсора, а не с первой пачки. После трёх прерываний на одном месте
  область засчитывается ошибками и обход идёт дальше — он не зацикливается.
  При замене whitelist-сервера обход прерывается и начинается заново.
- **Категории.** Каждый учёт попадает ровно в одну: сверен, пропущен (нет клиента
  на панели / изменился и не сверился при повторе / удалён во время обхода) или ошибка.
  Учёт, отложенный на повтор, считается один раз — по итогу повтора.

Наблюдаемость (в памяти процесса; после рестарта — «ещё не завершён»): строка
«Сверка расхода» в `/admin` → «Обход белых списков» и итоговая строка лога
`whitelist: сверка расхода завершена …` (WARNING при ошибках, а при прерывании —
`сверка расхода прервана …`). Показатели: длительность (активное время и пачки),
сверено / пропущено / ошибки, а также два разных времени:

| Метрика (`ReconcileStatus`) | Что означает |
|---|---|
| `last_complete_at`, `last_complete_started_at` | Обход дошёл до конца. Это только завершение работы: часть учётов могла остаться несверенной. Для **сверенных** учётов данные не старше `now − начало обхода`. |
| `last_success_at`, `last_success_started_at` | **Подтверждённая свежесть:** обход дошёл до конца, и каждый существующий учёт сверен. Условие — `ошибок = 0`, `изменились = 0` и `нет клиента на панели = 0` (`ReconcileReport.confirmed`; удалённые во время обхода не считаются). Данные **всех** учётов не старше `now − начало того обхода`. |

Неполный обход (с ошибками или пропусками) `last_success_*` не меняет: прежнее
подтверждение остаётся, пока его не заменит следующий полностью сверенный обход.
Строка в `/admin`: «все учёты сверены (данные учёта не старше …)» — только при
подтверждённом обходе; иначе «не сверено учётов: N (ошибок …, изменились во время
обхода …, нет клиента на панели …); их данные могут быть старше; сверенные не старше …»
и отдельной строкой — когда был последний полностью подтверждённый обход (или что его
ещё не было). Отдельной метрики-экспортёра нет.

**Гарантии и ограничения.** `WHITELIST_RECONCILE_MINUTES` — пауза между обходами
(не меньше минуты между ними), а **не** максимальное время сверки: время учёта
после последней сверки ≈ длительность обхода + пауза, и оно растёт с числом учётов,
паузами и медленной панелью. Гарантируется, что завершённый обход рассмотрел каждый
учёт с клиентом панели, существовавший на начало или добавленный во время него, хотя бы один раз; не
гарантируется, что каждый из них сверен: недоступный клиент, ошибка (в т. ч.
непрочитанный повтор) и учёт, изменявшийся во время обхода, отражаются как
ошибки/пропуски и ждут следующего обхода. Гарантия «данные всех учётов не старше …»
выдаётся только за полностью сверенный обход. Учёт без клиента на панели обход
считает несверенным, поэтому, пока такие учёты есть, подтверждения не будет —
ожидаемо: строка в `/admin` перечислит их количество. Состояние курсора и статистика не хранятся в БД; при нескольких процессах
бота каждый обходит независимо (учёты защищены блокировкой пользователя, но нагрузка
на панель суммируется) — запускайте фоновые задачи в одном процессе.

### Синхронизация подписки SubHub: быстрый триггер и резервный опрос (2026-10-05)

Изменение на панели попадает в подписку только после синхронизации SubHub. Путей два.

**Быстрый триггер** — после успешного изменения панели бот вызывает `POST /admin/sync`
(`trigger_configured_sync`). Он best-effort: недоступный SubHub не мешает операции, а
бот пишет предупреждение `SubHub: синхронизация не запрошена: …`.

| Источник | Когда | Изменения |
|---|---|---|
| Обработчики | сразу после применения | подтверждение оплаты и покупки, trial, выдача услуги, привязка, `/provision`, блокировка/разблокировка/синхронизация пользователя услуги, удаление подписки; с 2026-10-05 также `/extend`, `/sync`, `/wladjust`, `/wlresolve` (D-7); с 2026-10-06 — выбор цели и «Синхронизировать сервер» в разделе услуги, если первая порция переноса что-то применила |
| Worker очереди whitelist (`WHITELIST_QUEUE_POLL_SECONDS`, 30 с; не зависит от `SERVER_HEALTH_POLL_SECONDS`) | если в проходе что-то применено | очередь «Обход белых списков» (`process_due`: отложенное применение с backoff 1 мин → 1 ч и изменения, найденные сверкой расхода — исчерпание, истечение) |
| Фоновый цикл проверки серверов (`SERVER_HEALTH_POLL_SECONDS`, 60 с; 0 — выключен) | если в проходе что-то применено | отложенные обновления обычных серверов, с 2026-10-05 — возобновлённые прерванные оплаты (`recover_confirmed_payments`, D-8) |

Перед фоновым запросом бот пишет в журнал `SubHub: запрос синхронизации после фоновых
изменений (<причина>)`.

**Резервный опрос SubHub** (`refresh_interval_seconds`, в примере конфигурации 300 с)
подхватывает всё остальное: изменения, сделанные, пока SubHub был недоступен (неудачный
триггер не повторяется), истечение обычного конфига у пользователя без учёта услуги,
ручные изменения в панели.

**SubHub с 2026-10-05.** `POST /admin/sync` во время идущего прохода отвечает 202
`queued` и ставит повторный проход сразу после него. Прежний SubHub отвечал 409 без
повтора, а бот считал это успехом: изменение, сделанное после того, как проход прочитал
панель, ждало резервного опроса (D-6, `WHITELIST_ACCEPTANCE.md` §16). Пока рабочий
SubHub не обновлён, это ограничение остаётся.

**Задержка в production** (оценка по настройкам по умолчанию, не замер): обработчик —
секунды; очередь и отложенные обновления — до 60 с после восстановления панели плюс
backoff; исчерпание и истечение whitelist-конфига — до `WHITELIST_RECONCILE_MINUTES`
(15 мин) плюс длительность обхода и 60 с; остальное — до `refresh_interval_seconds`.
Проверено на стенде с ускоренными циклами (5 с / 1 мин, `WHITELIST_ACCEPTANCE.md` §16).

**Изолированный запуск фоновых задач.** `app.main.start_background_tasks(bot, settings)` —
единая сборка фоновых циклов для `run()` и для приёмки без Telegram polling
(`ops/acceptance/whitelist_background_e2e.py`); `stop_background_tasks` их останавливает.

**Worker очереди применения (с 2026-10-06).** `_whitelist_queue_worker` — единственный
в процессе обработчик `whitelist.process_due`; он запускается `start_background_tasks`
всегда, при любых `SERVER_HEALTH_POLL_SECONDS` (в т. ч. 0) и `WHITELIST_RECONCILE_MINUTES`.
Раньше `process_due` вызывался из цикла проверки серверов: при `SERVER_HEALTH_POLL_SECONDS=0`
покупка, сохранённая при недоступной панели, после её восстановления не применялась
сама. Теперь цикл проверки серверов очередь не обслуживает, поэтому при включённой
проверке двойной обработки нет.

- С 2026-10-06 очередь применяет и перенос на новую цель/flow (учёты с неподтверждённым
  размещением, см. «Смена целевого inbound»): тем же проходом, с тем же backoff.
- Период опроса — `WHITELIST_QUEUE_POLL_SECONDS` (по умолчанию 30 с, строго больше 0:
  отключить worker нельзя). Интервал повтора конкретного аккаунта по-прежнему задаёт
  backoff очереди (60 с → 1 ч, `next_sync_at`); worker лишь периодически запрашивает
  готовые к применению записи.
- Сериализация по пользователю, идемпотентность и применение актуального состояния —
  свойства `sync_user`/`process_due`, worker их не меняет. Ошибка одного аккаунта
  логируется, остальные в том же проходе обрабатываются; сбойный аккаунт остаётся в
  очереди и повторяется в следующем проходе (непредвиденная ошибка не двигает
  `next_sync_at`).
- После прохода, в котором что-то применено, worker просит SubHub синхронизироваться
  (`SubHub: запрос синхронизации … очередь «Обход белых списков»`); недоступный SubHub
  применение не отменяет.
- Один worker на процесс: повторный `start_background_tasks` при живом worker'е второго
  не создаёт (предупреждение в журнале). После `stop_background_tasks` worker можно
  запустить снова; состояние хранится в БД, перезапуск ничего не теряет и не начисляет
  повторно. Остановка отменяет задачу, в том числе при зависшем запросе к панели.
- Несколько процессов бота на одной БД не поддерживаются: защита «один worker» —
  в пределах процесса; от повторного применения между процессами защищает только
  идемпотентность (`desired_version`/`applied_version`, блокировка пользователя).

### Восстановление после недоступной статистики

1. Ничего вручную не делать: очередь (backoff до 1 ч) и фоновая сверка (обход после
   восстановления панели, до `WHITELIST_RECONCILE_MINUTES` + длительность обхода)
   привяжут `pending` события.
2. `/admin` → «Обход белых списков»: «Начисления ждут сверки расхода» должно стать 0.
   «Требуют решения» > 0 — открыть `/wl <tg>` каждого: варианты «до»/«после» на конец
   периода. Решение по фактам (время оплаты, обращения пользователя):
   `/wlresolve <tg> до|после <причина>` или `/wladjust <tg> <бесплатно> <куплено> <причина>`.
3. `ops/whitelist_check.py --details`: `unsettled=0 uncertain=0 mismatch=0`.

## 6. Порядок внедрения

Все шаги — в согласованное окно, по отдельному указанию владельца. Не запускать два
polling-процесса с одним `BOT_TOKEN`. Порядок проверен на изолированном стенде
5 октября 2026 (`docs/WHITELIST_ACCEPTANCE.md`); до внедрения закрыть или принять
условия из его §10 (в первую очередь дефект D-1).

0. **Предварительные проверки (без изменений).**
   - Версия 3x-ui на whitelist-панели: ≥ 3.2 (clients API); приёмка проведена на 3.9.0.
     Для другой версии повторить сценарий на стенде с тем же образом:
     `WLACC_XUI_IMAGE=ghcr.io/mhsanaei/3x-ui:<версия> ops/acceptance/stack.sh up …`, затем
     `ops/acceptance/whitelist_e2e.py`; учёт трафика этой версии (D-3) —
     `ops/acceptance/xui_traffic_d3.py <state> --image ghcr.io/mhsanaei/3x-ui:<версия>`.
   - На панели ровно один целевой inbound **VLESS + REALITY** (или Hysteria2): SubHub
     строит ссылки только для этих типов, иначе конфиг не появится в подписке. С
     2026-10-05 бот проверяет это при сверке сам (см. «Совместимость inbound с SubHub»).
   - Рабочий SubHub запускается из своего venv и исправление D-2 не затронуло. С 2026-10-05
     `requirements.txt` SubHub содержит `SQLAlchemy[asyncio]` (тянет `greenlet`), поэтому
     пересоздание venv и сборка образа из актуальных исходников работают без ручной установки
     `greenlet`; старый venv или образ нужно пересоздать из обновлённого файла (см.
     `WHITELIST_ACCEPTANCE.md` §14).
   - С 2026-10-05 SubHub сам скрывает конфиг с исчерпанной квотой (`totalGB` в байтах,
     расход из `clientStats`; `WHITELIST_ACCEPTANCE.md` §15). Чтобы это действовало,
     рабочий SubHub обновляется до этих исходников по своему регламенту; миграции БД
     нет, токены подписок сохраняются. Без обновления исчерпанный конфиг скрывается
     только после `enable=false` от панели — внедрение услуги это не блокирует.
   - С 2026-10-05 SubHub не теряет `POST /admin/sync`, пришедший во время идущей
     синхронизации (ответ 202 `queued` и повторный проход, `WHITELIST_ACCEPTANCE.md` §16).
     Обновить рабочий SubHub по его регламенту; миграции нет. До обновления такое
     изменение появляется в подписке только с резервным опросом (`refresh_interval_seconds`)
     — внедрение услуги это не блокирует.
1. **Резервная копия.** На хосте бота:
   `docker compose exec -T db pg_dump -U vpnbot -Fc vpnbot > /root/vpnbot-backups/<дата>/before-whitelist.dump`
   (права каталога 0700, файла 0600; `-T` — без TTY, иначе дамп портится). Проверить
   восстановление в отдельную базу, а не в рабочую:
   `docker compose exec -T db createdb -U vpnbot vpnbot_restorecheck`,
   `docker compose exec -T db pg_restore -U vpnbot -d vpnbot_restorecheck --no-owner --exit-on-error < …/before-whitelist.dump`,
   сравнить число строк `users`, `vpn_clients`, `client_server_mappings`,
   `payment_requests`, `servers` и `alembic_version` с рабочей базой, затем
   `dropdb vpnbot_restorecheck`. Сохранить текущий image (имя сверить
   по `docker compose images`): `docker tag vpnbot-bot:latest vpnbot-bot:rollback-whitelist`. Сохранить `.env`
   (вместе с действующим `SECRET_KEY`) и override.
2. **Проверить место** на корневом разделе (по отчёту 4 октября — около 1 ГБ свободно).
3. **Миграция и запуск.** Обновить исходники, `docker compose build bot`,
   `docker compose up -d bot`. Контейнер выполняет `alembic upgrade head`
   (`b7c8d9e0f1a2` → `d1e2f3a4b5c6` → `e2f3a4b5c6d7` → `f3a4b5c6d7e8` → `a4b5c6d7e8f9`):
   существующие серверы → `standard`, заявки → `subscription`, услуга выключена,
   пакеты и объёмы — начальные. Проверить `alembic current`, логи старта, polling.
   До шага 6 поведение для пользователей не меняется (раздел скрыт, пакеты не выдаются).
4. **Сервер через админку.** `/admin` → «Серверы» → «Добавить сервер» →
   «Обход белых списков», строка:
   `Обход белых списков|LV|https://cc.howegfkrosovki.online:<порт панели>/<путь>|<логин>|<пароль>|direct|<subscription_base или пусто>`.
   Бот сразу читает inbound'ы. Результат должен быть «Сервер готов к выдаче» с
   строкой «Целевой inbound N (vless/reality/tcp, совместим)»;
   при ошибке — исправить доступ и нажать «Синхронизировать сервер» в разделе услуги;
   при нескольких inbound'ах — выбрать единственный целевой; при «SubHub не построит
   ссылку» — исправить перечисленные параметры inbound в панели и синхронизировать.
   Прочитать строки о flow. «Готов» не означает, что SubHub уже знает о панели — шаг 5.
5. **SubHub.** В конфигурации SubHub добавить whitelist-панель (тот же `panel_url`,
   учётная запись только для чтения при возможности), `name: "Обход белых списков"`
   (или `node_name_mode: remark` с таким remark inbound'а). Перезапустить SubHub по
   его регламенту. Без этого шага конфиг не попадёт в общую ссылку. Проверить
   `GET /admin/servers` SubHub: у whitelist-панели `last_error=null`. До шага 6 клиентов
   на панели нет — подписки пользователей не меняются.
6. **Выдача нынешним пользователям.** `/admin` → «Обход белых списков» → «Выдать
   текущим пользователям». Проверить план: оплаченные (10 ГБ), trial (3 ГБ), бессрочные
   (безлимит), **неоднозначные** (нет покрывающей оплаты и следа trial — привязанные
   старые подписки, ручные продления; список показывается). Выбрать «только однозначным»
   или «неоднозначные как оплаченные». Нажатие включает услугу; повтор безопасен.
   Конфиги создаются фоновой очередью (до 50 за проход worker очереди, `WHITELIST_QUEUE_POLL_SECONDS`, 30 с).
7. **Сверка.** Дождаться «ожидают применения: 0» в разделе услуги, затем:
   `docker compose cp ops/whitelist_check.py bot:/tmp/whitelist_check.py`
   `docker compose exec -e PYTHONPATH=/app bot python /tmp/whitelist_check.py --details`
   (`PYTHONPATH` нужен, если пакет `app` не установлен в образ; скрипт только читает)
   — ожидается `mismatch=0 read_errors=0 unsettled=0 uncertain=0 placement_mismatch=0
   placement_pending=0`. Выборочно: `/wl <tg_id>` у оплаченного,
   trial и бессрочного пользователя; на панели — `totalGB` в байтах (10 ГБ =
   10737418240, 3 ГБ = 3221225472, бессрочный — 0), `expiryTime` равен сроку подписки,
   UUID/subId/email совпадают с клиентом обычной панели, Telegram ID, единственный
   целевой inbound, `trafficReset=never`. У обычных панелей `totalGB` остаётся 0.
8. **SubHub и устройство.** Для оплаченного и бессрочного пользователя:
   `POST /admin/subscriptions/resolve` возвращает **прежний** `subscription_url`, а
   подписка содержит на один конфиг больше («Обход белых списков»). На тестовом
   устройстве с Happ (приёмкой не проверялось): обновить существующую подписку
   (не добавлять новую ссылку), убедиться, что появился конфиг услуги, подключиться
   через него и через обычный конфиг, открыть сайт. Тестовые оплаты в production не
   создавать; для проверки исчерпания достаточно стенда.
9. **Наблюдение после запуска.** 3x-ui 3.9.0 теряет часть трафика вокруг запусков панели
   и перезапусков Xray (D-3, протокол `docs/acceptance/xui_traffic_d3_2026-10-06.md`,
   сводка — §9 «D-3»): до ≈ 10 с после старта
   процесса панели или «Перезапустить панель», до ≈ 5 с после перезапуска Xray — в том
   числе после каждого отключения клиента самой панелью по квоте или сроку. Такой трафик не
   списывается с остатков и нигде не виден (бот, SubHub и `whitelist_check` его не
   замечают). Поэтому: не перезапускать whitelist-панель и Xray без необходимости;
   плановые работы — в часы наименьшего трафика; если важна точность учёта, а не
   ≈ 20–30 с простоя услуги, — выключить inbound услуги, выполнить работы с полным
   перезапуском процесса панели (`systemctl restart x-ui` / перезапуск контейнера),
   подождать ≥ 15 с после старта, включить inbound и запросить синхронизацию SubHub
   (`/sync` в боте; иначе выключенный inbound может на время пропасть из подписок).
   `restartXrayOnClientDisable` оставить включённым (по умолчанию): без него открытые
   соединения клиента, отключённого по квоте, сроку или блокировке, продолжают работать
   (стенд: 32 МиБ при квоте 4 МиБ). Ежедневно в первые дни — `/admin` → «Обход белых списков»:
   «ожидают применения», «ждут сверки», «требуют решения», «Сверка расхода» — «все учёты сверены» (иначе строка перечислит несверенные учёты).
   В журнале бота — нет повторяющихся `SubHub: синхронизация не запрошена` (такие
   изменения дойдут до подписки только с резервным опросом SubHub).

10. **Смена целевого inbound или его flow (при необходимости, после внедрения).**
    В часы наименьшего трафика: в 3.9.0 каждое снятие прежней привязки ставит
    перезапуск Xray с потерей учёта D-3 у всех клиентов (≈ 5 с на перезапуск, серия на
    время переноса). Перед сменой — `ops/whitelist_check.py --details`: `placement_*` = 0.
    - Новый inbound создать на панели (VLESS REALITY или Hysteria2), прежний **не
      удалять**, пока перенос не завершён: без него старая ссылка у устройств, ещё не
      обновивших подписку, перестанет работать сразу.
    - Цель: «Синхронизировать сервер» → выбрать inbound (если найдено несколько); flow —
      `/delinbound <server> <inbound>` + `/addinbound <server> <inbound> vless <flow>`,
      затем «Синхронизировать сервер» (до синхронизации сервер не готов, очередь ждёт).
    - Раздел услуги: «Размещение на inbound N … подтверждено X из Y; ожидает …; ошибка …».
      «Сервер готов» — это только формат inbound'а; перенос завершён, когда «ожидает 0,
      ошибка 0». Ошибки — `/wl <tg>` (строка «Размещение» и «Ошибка применения»);
      недоступная цель или сбой панели повторяются очередью с backoff до 1 ч.
    - Учёты, выданные до миграции `a4b5c6d7e8f9`, остаются и на прежнем inbound'е
      (происхождение привязки неизвестно). Если inbound был целью услуги и других
      клиентов этой подписки на нём быть не должно — `/wlclaim <inbound> <причина>`.
    - Итог: `ops/whitelist_check.py --details` — `placement_mismatch=0 placement_pending=0`;
      `/sync` в боте, если нужно ускорить обновление подписок; затем прежний inbound
      можно удалить на панели. Проверить устройство: подписка обновлена, конфиг услуги
      подключается к новому inbound'у.

## 7. Откат

Порядок откатов схемы проверен на PostgreSQL 16 с данными услуги
(`ops/acceptance/whitelist_migration_check.py`, `docs/acceptance/whitelist_migration_2026-10-05.md`).

- **До шага 6 (услуга не выдавалась).** Достаточно прежнего image; схема остаётся,
  данные пользователей не затронуты. Убрать whitelist-панель из конфигурации SubHub.
- **Код без схемы**: остановить бот, `docker tag vpnbot-bot:rollback-whitelist …`,
  запустить прежний image. Новые таблицы/колонки старым кодом игнорируются;
  `SECRET_KEY` не менять. Перед этим выключить whitelist-сервер в админке, иначе
  клиенты на панели останутся с последней квотой (старый код их не меняет).
  Заявки `kind=traffic` старый код подтвердил бы как продление — до отката
  отклонить или обработать все ожидающие покупки трафика (`/pending`).
- **Схема**: перед откатом довести «ждут сверки» и «требуют решения» до 0. Проверено:
  после `alembic downgrade b7c8d9e0f1a2` и повторного upgrade ожидающее событие
  становится `settled` **без применения** — начисление было бы потеряно. Откат
  `e2f3a4b5c6d7` возвращает маркер ожидания в `last_error` только ожидающим покупкам и
  не трогает иные ошибки. Откат `f3a4b5c6d7e8` удаляет последнее чтение; прежний код не
  знает отрицательной точки (сброс при нерешённом событии): перед откатом решить такие
  учёты (`/wlresolve` или `/wladjust`) и дождаться успешной сверки — после неё точка
  неотрицательна. `alembic downgrade f9b2c3d4e5f6` удаляет учёт, журнал, пакеты и
  `kind`-колонки (данные услуги будут потеряны; прежние таблицы возвращаются без
  изменений) — только после выгрузки `whitelist_accounts`/`whitelist_ledger`
  (`pg_dump -Fc -t whitelist_accounts -t whitelist_ledger -t traffic_packages …`).
  Полное восстановление dump — отдельная операция с потерей записей после него;
  выполнять в новую базу и переключать `DATABASE_URL`, а не поверх рабочей.
- **Откат `a4b5c6d7e8f9`** (`alembic downgrade f3a4b5c6d7e8`) удаляет подтверждённое
  размещение и строки привязок услуги — сведения о незавершённом переносе теряются, а
  прежний код переносить не умеет (он только дополняет привязки к текущей цели и flow не
  очищает). Перед откатом — «ожидает 0, ошибка 0» в строке «Размещение» и
  `placement_mismatch=0`; смену цели после отката выполнять вручную на панели. Проверено:
  upgrade → downgrade → upgrade на SQLite и PostgreSQL 16.15 с существующими учётами.
- Клиентов whitelist-панели при откате удалить на самой панели или выключить сервер
  в SubHub, чтобы конфиг исчез из подписок. Обычные панели откат услуги не затрагивает
  (их клиенты не получают квот).

  подтверждения цели) — каждую ловят тесты; PG-сценарий без advisory lock падает
  (`StaleDataError`). Весь набор: без PostgreSQL — 608 passed, 12 skipped; с PostgreSQL
  16.15 (одноразовый контейнер, отдельная база) и контрактом SubHub — **620 passed**;
  сценарии переноса и учёта на PostgreSQL (временная подмена фикстуры `session`) — 104
  passed. Миграция `a4b5c6d7e8f9`: upgrade/downgrade/upgrade с учётами на SQLite и
  PostgreSQL 16.15, `alembic check` — только прежние расхождения. Ruff чист; mypy `app` —
  77 диагностик в 11 файлах, совпадают с baseline (новые файлы тестов и
  `ops/whitelist_check.py` — без диагностик). Реальная 3x-ui, Telegram, Happ и production
  не использовались.

## 9. Ограничения и решения

- Заявка на покупку трафика без VPN-клиента пользователя остаётся «ожидает применения»,
  пока клиент не появится (панель применять нечего, `applied_version` не растёт);
  покупка требует активной подписки, поэтому в обычном потоке этого не происходит.

- Один сервер и один inbound. Несколько активных whitelist-серверов запрещены
  индексом. Замена сервера начинает новую точку отсчёта; клиента старой панели
  администратор удаляет вручную.
- Если статистика недоступна в момент оплаты, а после события панель видела трафик
  (`last_online` позже оплаты), разделить расход автоматически нельзя: событие
  `uncertain`, до решения администратора квота — нижняя граница, остатки не
  списываются. Панели без `lastOnline` (или со значением 0) дают точную привязку
  только при нулевом расходе и для покупок без перерасхода.
- Допуск часов `LAST_ONLINE_SKEW` = 1 мин: расход в последнюю минуту перед оплатой при
  недоступной статистике считается неразделимым (консервативно).
- Перерасход между опросами панели (порядка десятков секунд) не списывается с будущих
  покупок: квота пересчитывается от фактического счётчика.
- Сброс счётчика на панели: неизвестный расход между последним чтением и сбросом не
  списывается; отображается как расхождение (`/wl`), корректировка — `/wladjust`.
  Окно, в котором после сброса доступна старая квота, ограничено временем до сверки
  этого учёта — паузой между обходами плюс длительностью обхода, а не 15 минутами.
  С 2026-10-06 это верно и для учёта с неопределённым событием: раньше сверка такого
  учёта завершалась до проверки эпохи, поэтому сброс не обнаруживался до решения
  администратора, старая точка оставалась в квоте, а `/wlresolve` мог поставить точкой
  границу прежней эпохи (`WHITELIST_ACCEPTANCE.md` §18).
- `resetTraffic` не меняет строку статистики. Если после сброса и до ближайшего чтения
  счётчик успевает превысить последнее прочитанное значение, сброс не виден: бот спишет
  только прирост сверх последнего чтения, квота панели по-прежнему отсчитывается от
  прежней базы, и пользователь получит дополнительно объём, равный этому значению. Для
  этого между двумя чтениями нужно израсходовать больше, чем было накоплено до сброса.
  Пересоздание клиента обнаруживается всегда — по смене `traffic_row_id`.
- Замена сервера или удаление клиента при неразрешённом событии: прочитанный на
  прежнем счётчике период не переносится в новую точку отсчёта (как и прежде, решение
  только `/wladjust`); квота нового клиента — остатки с событиями без этого расхода.
- **Лимит трафика в SubHub (исправлено 2026-10-05, репозиторий SubHub).** Раньше
  `client_is_active` сравнивал расход с `totalGB × 1024³`, а `up/down` искал в
  `settings.clients[]`, где 3x-ui их не отдаёт, — проверка лимита не срабатывала;
  исчерпанный конфиг скрывался только по `enable=false` от панели. Теперь `totalGB`
  читается как байты (`total_bytes`), расход — `up + down` из `clientStats` того же
  inbound'а по email; конфиг скрывается при `up + down >= totalGB > 0` (как у панели),
  `totalGB=0` — безлимит, отсутствие статистики не скрывает конфиг (решает панель).
  Миграция SubHub не нужна; до обновления рабочего SubHub поведение прежнее (скрытие
  по `enable=false` в пределах опроса панели и SubHub). Подробности —
  `WHITELIST_ACCEPTANCE.md` §15.
- Бесплатный пакет выдаётся при подтверждении оплаты (статус `CONFIRMED`). Если после
  этого администратор отклонит заявку в статусе `failed`, выдача остаётся (отмечена в
  журнале); `confirmed`/`applied` заявки отклонить нельзя.
- Привязка старой подписки после запуска услуги не выдаёт пакет автоматически —
  повторный запуск «Выдать текущим пользователям» подхватывает таких пользователей.
- **D-1 (исправлен 2026-10-05, код; на стенде не проверен).** Выбор тарифа подписки, пока
  покупка трафика с квитанцией ждёт проверки, раньше возвращал заявку на трафик. Теперь бот
  отвечает «Заявка PAY-… (покупка трафика, N ГБ) уже на проверке» и ничего не меняет; то же
  в обратную сторону. Подробности и ограничения — `docs/WHITELIST_ACCEPTANCE.md`, §11.
  До прогона обновлённого E2E на стенде оставьте проверку: ошибочно приложенные квитанции
  администратор по-прежнему отклоняет.
- **D-4 (исправлен 2026-10-05, код).** Заданный объём (пакет, начисление, бесплатный
  пакет) показывается так, как введён (`texts.fmt_gb_set`: 0,02 ГБ, 1,1 ГБ), а остаток и
  расход — с округлением вниз (`texts.fmt_gb`). Учёт и API панели остаются целыми байтами,
  `gib_to_bytes` усекает как прежде; купленные остатки не увеличивались. Новые экраны с
  объёмом выбирают форматтер по смыслу: заданное — `fmt_gb_set`, остаток — `fmt_gb`.
  Подробности — `docs/WHITELIST_ACCEPTANCE.md`, §12.
- **Синхронизация подписки SubHub (2026-10-05, `WHITELIST_ACCEPTANCE.md` §16).** Быстрый
  триггер best-effort и не повторяется: если SubHub недоступен в момент изменения, изменение
  появится со следующим триггером по другому поводу или с резервным опросом
  (`refresh_interval_seconds`); бот пишет предупреждение `SubHub: синхронизация не запрошена`.
  Если SubHub завис, а не отказал в соединении, запрос бота обычно остаётся в очереди сокета и
  выполняется после восстановления (наблюдалось на стенде), но обработчик ждёт около
  `SUBHUB_TIMEOUT_SECONDS` (15 с), прежде чем ответить администратору. Истечение обычного
  конфига у пользователя без учёта услуги и ручные изменения в панели доходят до подписки
  только с опросом. Исчерпание и истечение whitelist-конфига — после обхода сверки
  (`WHITELIST_RECONCILE_MINUTES`) и очереди. До обновления рабочего SubHub (D-6) триггер,
  пришедший во время идущей синхронизации, теряется до опроса.
- **D-3: 3x-ui 3.9.0 теряет трафик вокруг запусков панели и перезапусков Xray**
  (исследовано 2026-10-06, протокол `docs/acceptance/xui_traffic_d3_2026-10-06.md`;
  в `WHITELIST_ACCEPTANCE.md` отдельного раздела анализа нет — §17 там о worker очереди,
  дефект — §8 «D-3»). Задача трафика 3x-ui считает
  расход дельтами от базы, которая хранится не в процессе Xray, а в экземпляре сервиса.
  Поэтому не попадает в `client_traffics` (и не списывается ботом): трафик до первого
  опроса после старта процесса панели или «Перезапустить панель» (≈ 10 с); трафик клиента
  после перезапуска Xray кнопкой/API/сменой шаблона, если его новый счётчик к опросу не
  меньше прежнего (≤ 5 с); трафик **всех** клиентов ≈ 5 с после того, как панель сама
  отключила клиента по квоте или сроку (`restartXrayOnClientDisable=true` по умолчанию
  перезапускает Xray). Ошибка всегда в пользу пользователя; бот её не видит и
  компенсировать не может (счётчиков Xray API панели не отдаёт). Регламент — §6 шаг 9;
  исправление upstream предложено (`docs/acceptance/3x-ui-v3.9.0-d3-stats-baseline.patch`),
  рабочая панель не обновлялась. Обновление clients через API (квота, срок, `enable=true`)
  Xray не перезапускает и трафик не теряет. Перерасход между опросами — отдельное
  явление: он учитывается (см. выше). С 2026-10-06 к перезапускам добавляется снятие
  прежней привязки при переносе (3.9.0, по исходникам; см. «Смена целевого inbound») —
  D-3 этим не исправлен.
- **Перенос при смене цели (2026-10-06).** Доступ во время переноса не гарантируется:
  новая ссылка доходит до устройства только после синхронизации SubHub и обновления
  подписки, старая перестаёт работать при снятии прежней привязки (паузы перед detach
  нет). В 3.2.0 flow — свойство общей записи: flow прежней цели (во время
  сосуществования) и чужих привязок меняется на flow цели. Привязки учётов,
  выданных до миграции `a4b5c6d7e8f9`, и привязки, созданные при недоступном чтении
  клиента с потерей ответа панели, считаются чужими и не снимаются без `/wlclaim`.
  Привязки под прежней идентичностью подписки (сменился email) и на прежнем сервере
  услуги не снимаются (как и прежде — вручную на панели). Несколько процессов бота
  на одной БД не поддерживаются (как и для очереди). Реальный перенос на панели 3x-ui
  не выполнялся: проверено моделью панели по исходникам и HTTP-контрактом.
- **Тип inbound.** SubHub выдаёт ссылки только для VLESS + REALITY и Hysteria2;
  whitelist-inbound другого типа не попадёт в подписку. Импорт inbound не переносит
  `flow` — клиенты услуги создаются без него (с REALITY TCP проверено трафиком).
  *(С 2026-10-05 несовместимый или неполный inbound не даёт статус «готов», а flow
  явно показывается администратору — см. «Совместимость inbound с SubHub». Ограничения
  этой проверки: правила повторяют текущий код SubHub и проверены против его исходников,
  а не против рабочего экземпляра; `reality_overrides` SubHub бот не видит — inbound,
  которому недостающие REALITY-параметры подставляет только override SubHub, бот
  считает несовместимым; Hysteria2 и VLESS REALITY xhttp трафиком не проверялись.)*
