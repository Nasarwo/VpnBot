## 2. Стенд

Воспроизводимый стенд: `ops/acceptance/stack.sh up <state> <subhub-src>` / `down <state>`.

| Компонент | Версия / настройка |
|---|---|
| PostgreSQL | `postgres:16-alpine` (16.15), как в `docker-compose.yml` |
| Обычная панель | `ghcr.io/mhsanaei/3x-ui:v3.9.0`, VLESS + REALITY (TCP), отдельный путь панели и учётные данные |
| Whitelist-панель | тот же образ, отдельный контейнер, один целевой inbound VLESS + REALITY |
| SubHub | исходники `SingleLinkVpn/subhub` (коммит `d9a2c80` + незакоммиченная правка заголовка подписки, не относящаяся к услуге), `token_strategy: by_email`; образ дополнен `greenlet` (D-2) |
| Источник трафика | nginx в той же сети: HTTP-файл 8 МиБ и локальная TLS 1.3 цель REALITY (без выхода в интернет) |
| Клиент | `xray` 26.9.30 из образа 3x-ui; ссылка берётся из подписки SubHub |
| Бот | обработчики `app.bot.*` вызываются напрямую; транспорт Telegram заменён записывающей заглушкой (`tests.test_admin_confirm.FakeBot`); `XuiPanelUpdater`, PostgreSQL advisory lock, alembic — настоящие |

Отличия стенда от рабочих панелей, внесённые только для доставки трафика к локальному
файловому серверу в частной Docker-сети: из шаблона xray убрано правило
`geoip:private → blocked`, а исходящему `direct` добавлен `finalRules: allow 172.16.0.0/12`
(в Xray 26 freedom по умолчанию блокирует частные адреса для VLESS). На бизнес-логику не
влияет.

Сценарий: `ops/acceptance/whitelist_e2e.py <state>`; протокол финального прогона —
`docs/acceptance/whitelist_e2e_2026-10-05.md`. Проверка миграций:
`ops/acceptance/whitelist_migration_check.py`; протокол —
`docs/acceptance/whitelist_migration_2026-10-05.md`.

## 8. Дефекты и наблюдения

**D-1. Выбор тарифа подписки при ожидающей проверки покупке трафика (средний, VpnBot).**
`payments.create_request` возвращает уже открытую заявку с квитанцией, не проверяя её вид.
Если у пользователя на проверке покупка трафика, выбор «1 месяц» показывает «Заявка
PAY-… создана», но это заявка на трафик (49 ₽); следующая квитанция за подписку прикрепится
к ней, продления не будет. Воспроизведено в E2E (раздел «Заявка на подписку при ожидающей
проверки покупке трафика») и в прогоне №5, где «продление» после квитанции за трафик дало
срок +0. Обратный путь защищён: `create_traffic_request` при квитанции бросает
`PendingRequestExists`. Предлагаемое исправление: в `create_request` при квитанции и
`kind != subscription` поднимать `PendingRequestExists`, а в `select_plan` показывать
«Заявка … уже на проверке», как в разделе услуги. Не исправлялось: приёмка не меняет код.
*(Статус после приёмки: исправлено 2026-10-05, см. §11; текст выше — состояние на момент прогона.)*

**D-2. Свежая сборка SubHub не стартует (средний, SubHub, вне кода услуги).**
`requirements.txt` (`SQLAlchemy>=2.0,<3`) разрешается в SQLAlchemy 2.1.3, которая больше
не тянет `greenlet`; `docker build` + запуск падает на `ImportError … greenlet`. Рабочий
SubHub работает из существующего venv (systemd) и не затронут, но переустановка или
сборка образа сломают его. Исправление: `SQLAlchemy[asyncio]` или явный `greenlet` в
`requirements.txt`. На стенде — производный образ с `greenlet`.
*(Статус после приёмки: исправлено 2026-10-05, см. §14; текст выше — состояние на момент прогона.)*

**D-3. Первый трафик после запуска 3x-ui 3.9.0 не учитывается панелью (риск, upstream).**
Воспроизведено трижды на свежих стендах после `docker stop/start` whitelist-панели:
загружено 8 388 608 Б, учтено панелью 0 Б; следующий трафик учитывается полностью. Статистика
xray при этом содержит весь трафик (`statsquery`: 2 × 8 МиБ при учтённых 8 МиБ). В
`internal/xray/api.go` (`GetTraffic`) первый проход после пустого снимка счётчиков только
запоминает базу — по наблюдению, это и «съедает» первый трафик. Обновление клиента через
API (без перезапуска) трафик не теряет — проверено дважды. Бот согласован с панелью, поэтому
такой трафик не списывается ни с одного остатка и квоту не уменьшает: каждый перезапуск
панели даёт пользователям неучтённый трафик примерно за один интервал опроса. Мера: не
перезапускать whitelist-панель без необходимости; при перезапусках учитывать погрешность.
*(Статус после приёмки: исследовано 2026-10-06, см. протокол
`docs/acceptance/xui_traffic_d3_2026-10-06.md` и сводку `WHITELIST_SERVICE.md` §9 «D-3»
(ссылка «§17» прежних редакций устарела: §17 этого документа — worker очереди) — причина подтверждена по
исходникам и измерениями; потеря возникает не только после запуска панели, но и после
перезапусков Xray, в том числе тех, что панель делает сама при отключении клиента по квоте
или сроку. Текст выше — состояние на момент прогона.)*

**D-4. Дробные объёмы отображаются меньше введённых (низкий, VpnBot).** `gib_to_bytes`
усекает байты, `fmt_gb` округляет вниз: введённые 0,02 ГБ показываются как «0,01 ГБ»
(уведомление пользователю в E2E), 1,1 ГБ — как «1,09 ГБ». Целые объёмы (10/25/50, 3)
точны. Исправление: округлять байты до ближайшего целого при вводе.

**Подтверждённые ограничения (не дефекты услуги):**

- SubHub строит ссылки только для **VLESS + REALITY** и **Hysteria2**
  (`link_builder.build_link`); inbound whitelist-сервера должен быть одного из этих типов,
  иначе конфиг не попадёт в подписку. Подтверждено на стенде (простой VLESS не дал ссылок).
- SubHub (`client_is_active`) трактует `totalGB` как гигабайты; исчерпанный конфиг всё равно
  скрывается — по `enable=false`, который выставляет панель (подтверждено на стенде).
- Импорт inbound не переносит `flow`: клиенты услуги создаются без `flow`, ссылка — без
  `flow`. С REALITY TCP это работает (проверено трафиком).

*(Статус после приёмки: с 2026-10-05 несовместимый inbound не даёт статус «готов», flow
показывается администратору — см. §13; текст выше — состояние на момент прогона.)*

*(Статус после приёмки: проверка лимита в SubHub исправлена 2026-10-05 — `totalGB` читается

## 12. Исправление D-4 (результаты от 2026-10-05, после приёмки)

Разделы 1–10 (в том числе описание D-4 и предложенное там «округлять байты до ближайшего
целого») фиксируют прогон приёмки **до** исправления и не пересматриваются.

**Почему предложение из §8 не подходит.** 0,02 ГБ = 21 474 836,48 Б → ближайшее целое —
21 474 836 (то же, что даёт усечение), 1,1 ГБ = 1 181 116 006,4 Б → 1 181 116 006 (тоже то же).
Округление байтов ничего не меняет: дефект в выводе (`fmt_gb` округляет вниз до сотых),
а не только в вводе. Округление байтов вверх, наоборот, увеличило бы купленные остатки.

**Причина.** Один форматтер `fmt_gb` обслуживал два разных смысла: заданный объём
(пакет, начисление, бесплатный пакет) и остаток. Для остатка округление вниз правильно
(не обещаем лишнего), для заданного объёма оно показывает меньше введённого, потому что
`gib_to_bytes` усекает дробные байты.

**Изменения (учёт и API панели не менялись: байты остаются целыми, `gib_to_bytes` прежний).**
- `whitelist.set_volume_gib_text` — самая короткая запись с 2–4 знаками, которую
  `gib_to_bytes` переводит ровно в те же байты (0,02 → «0,02», 1,1 → «1,1», 0,005 → «0,005»).
  Для байтов, не соответствующих такому вводу, значение усекается до сотых — вверх не
  округляется.
- `texts.fmt_gb_set` — заданный объём; `texts.fmt_gb` — остаток и расход, округление вниз
  (без изменений). На `fmt_gb_set` переведены: кнопки и списки пакетов (пользователь и
  админ), заявки (создание, «уже на проверке», карточка, история, ожидающие), уведомление и
  ответ администратору о начислении, «будет восстановлен до»/«+N» в ожидающих начислениях,
  журнал начислений, настройки бесплатных пакетов, план выдачи. На `fmt_gb` остались:
  «Бесплатный/Купленный остаток», карточка пользователя (вместе с байтами), расход и варианты
  при неоднозначном начислении.
- `payments.whitelist_package_title` (заголовок снимка новых заявок) использует ту же запись.
  Сохранённые заявки не пересчитываются: у них остаются прежние байты и заголовок; экраны
  показывают их байты через `fmt_gb_set`, так что объём старых заявок на 0,02 ГБ тоже
  читается как «0,02 ГБ».

## 13. Ложная готовность whitelist-сервера при несовместимом inbound (результаты от 2026-10-05, после приёмки)

Разделы 1–10 фиксируют прогон приёмки **до** исправления и не пересматриваются: на тот
момент сервер с единственным импортированным inbound считался готовым независимо от его
типа, а «простой VLESS не дал ссылок» было отмечено как ограничение (§8).

**Причина.** `whitelist.sync_inventory` и `choose_inbound` выставляли `ready`, если
включённая строка `server_inbounds` ровно одна. Строка хранит только протокол (`vless`),
без security/транспорта/параметров REALITY, поэтому VLESS без REALITY, Trojan, VMess,
Shadowsocks, REALITY без ключа/SNI/shortId считались готовыми, хотя SubHub
(`link_builder.build_link`) не строит для них ссылку. Выбор цели ставил `ready` без
обращения к панели. flow при импорте всегда `None` — администратор об этом не узнавал.

**Фактически поддерживаемые сочетания SubHub** (исходники `SingleLinkVpn/subhub`,
коммит `d9a2c80` + незакоммиченные правки `app/utils.py`, `tests/test_core.py`, не
относящиеся к ссылкам): ссылку и профиль Mihomo получают VLESS + REALITY по `tcp`/`raw`/
`xhttp` (нужны публичный ключ или выводимый приватный, `serverNames`, непустой `shortIds`)
и Hysteria2. Для VLESS REALITY `grpc`, `tcp` с `header=http` и VLESS Encryption SubHub
строит ссылку без нужного серверу параметра (`serviceName`, `headerType`, `encryption`);
flow передаётся только для `tcp`/`raw`. SubHub не менялся (новые протоколы не добавлялись).

**Изменения (VpnBot).**
- `app/services/whitelist_compat.py` — проверка inbound по данным `inbounds/list`:
  вердикт «совместим/несовместим» с перечнем причин и пояснения о flow. Секреты REALITY
  и данные чужих клиентов в сообщения не попадают; у чужих клиентов читается только flow.
- `whitelist.sync_inventory` — новый статус `incompatible` для несовместимой цели (цель
  остаётся выбранной, после исправления панели повторная сверка делает сервер готовым);
  кандидаты при нескольких inbound перечисляются с вердиктом; аудит содержит причины.
  `choose_inbound` выбирает цель и сразу выполняет сверку с панелью.
- `provisioning.import_inbounds` = `fetch_inbounds` + `reconcile_inbounds` (поведение
  обычных серверов прежнее).
- Бот: тексты статуса, напоминание о границе проверки (конфигурация SubHub) в сообщении
  «готов», кнопки выбора другого inbound при `incompatible`.

## 14. Исправление D-2: SubHub собирается без ручной установки greenlet (результаты от 2026-10-05, после приёмки)

**Причина.** SQLAlchemy 2.1 перестала тянуть `greenlet` по умолчанию, а `app/db.py` SubHub
использует `create_async_engine`. `requirements.txt` содержал `SQLAlchemy>=2.0,<3`, поэтому
чистая установка и штатный образ получали SQLAlchemy 2.1.3 без `greenlet`, и первая же async-операция
падала с `ImportError … greenlet`. Стенд приёмки этого не показывал: образ дополнялся слоем

- `requirements.txt`: `SQLAlchemy>=2.0,<3` → `SQLAlchemy[asyncio]>=2.0,<3`. Это документированный

  `requirements-dev.txt` наследует `-r requirements.txt`; `Dockerfile` ставит зависимости только из
  `requirements.txt` и не упоминает `greenlet`.
- `Dockerfile` и `requirements-dev.txt` не менялись: оба пути установки берут `requirements.txt`.
  Для production-venv (`systemd/subhub.service` запускает `/opt/subhub/.venv`) отдельного
  скрипта установки в репозитории нет; при пересоздании venv нужно ставить `-r requirements.txt`.

## 15. Лимит трафика 3x-ui → SubHub: единица `totalGB` и источник расхода (результаты от 2026-10-05, после приёмки)

**Причина.** В SubHub было два независимых дефекта, каждый из которых один отключал проверку
лимита:

1. *Единица.* `normalizer.py` записывал `totalGB` в `total_gb`, а `link_builder.client_is_active`
   сравнивал расход с `total_gb × 1024³`. В 3x-ui `totalGB` — байты: `client_traffics.total =
   client.TotalGB` (`internal/web/service/inbound_traffic.go: AddClientStat/UpdateClientStat`),
   LDAP-синхронизация самой панели пишет `defGB × 1024³` (`ldap_sync_job.go`); комментарий
   «in GB» в `model.Client` неточен (§2 `WHITELIST_SERVICE.md`). Для 10 ГиБ порог получался
   11 529 215 046 068 469 760 Б.
2. *Источник расхода.* `up/down` искались в `settings.clients[]`. В `model.Client` счётчиков нет:
   `GET /panel/api/inbounds/list` отдаёт их отдельным массивом `clientStats[]` inbound'а
   (`xray.ClientTraffic`: `email`, `up`, `down`, `total`, `enable`, …; `GetInbounds` →
   `Preload("ClientStats")` + `backfillClientStats` для клиентов, привязанных к нескольким
   inbound'ам). Поэтому `used_bytes` всегда был `None` и проверка не выполнялась вовсе —
   исправление только сравнения ничего бы не дало.

Дефект маскировала сама панель: задача трафика (`disableInvalidClients`, условие `total > 0 AND
up + down >= total`) выставляет `enable=false` и в `client_traffics`, и в `settings.clients[]`,
и SubHub скрывал исчерпанный конфиг по `enable` (§6, §8 — состояние на момент прогона).
Источник проверен по исходникам 3x-ui v3.9.0 (тег, коммит `3cd4bf5`).

**Путь данных и результат проверки каждого участка.**

| Участок | Что происходит | Вывод |
|---|---|---|
| API панели | `inbounds/list`: квота — `settings.clients[].totalGB` (байты), расход — `clientStats[].up/down` | подтверждено на 3x-ui 3.9.0: в `settings.clients[]` нет `up/down` |
| Получение | `ThreeXUIClient.fetch` возвращает inbound'ы как есть, `clientStats` не отбрасывает | без изменений |
| Нормализация | `normalize_inbound` → `NormalizedClient` | исправлено |
| Сохранение | `client_nodes` (ссылка, `enabled`, `expiry_time`), `observed_clients.raw_hash`, `clients.token`; квота и расход не хранятся | миграция не нужна |
| Загрузка старых данных | выдача читает сохранённые узлы; узел пересчитывается каждой успешной синхронизацией панели | первая синхронизация исправляет узлы |
| Фильтрация ссылок | `build_link` → `client_is_active` | исправлено |

**Исправление (SubHub, `SingleLinkVpn/subhub`).**
- `app/models.py`: поле `total_gb` → `total_bytes` (байты, 0/`None` — безлимит); `used_bytes` —
  `up + down` строки `clientStats`.
- `app/normalizer.py`: `_usage_by_email` сопоставляет строки `clientStats` с клиентом по email
  (`strip().casefold()`, как ключ клиента SubHub; панель сопоставляет без учёта регистра);
  `_byte_count` принимает только целые ≥ 0 — bool, строки, дробные, отрицательные и пропуски
  дают «нет статистики»; `total_bytes = totalGB` без пересчёта. Счётчики не входят в `raw_hash`
  клиента — иначе каждый опрос с трафиком писал бы запись аудита на клиента.
- `app/link_builder.py`: конфиг неактивен при `total_bytes > 0` и `used_bytes >= total_bytes` —
  то же условие и та же граница, что у панели.
- Эвристик по величине числа нет. Других пересчётов единиц в SubHub нет (поиск `1024`, `**3`,
  `total_gb` по `app/`).
- Квота берётся из `settings.clients[].totalGB`, как и раньше; `clientStats.total` панель держит
  равным ей (`AddClientStat/UpdateClientStat`) — на стенде они совпадали во всех состояниях.
- Нет статистики — SubHub не скрывает конфиг по лимиту (как и до исправления), решает панель
  через `enable=false`. Нечисловой `totalGB` раньше ронял синхронизацию всей панели
  (`TypeError` при сравнении), теперь считается безлимитом для SubHub; панель его не выдаёт.

**Совместимость сохранённых данных.** Миграции и отдельной полной повторной синхронизации
не нужно: в БД SubHub нет квоты и расхода, а узлы пересчитываются каждой успешной синхронизацией
(SubHub запускает первую синхронизацию сразу при старте). До неё выдаются ранее сохранённые
узлы; если опрос панели завершился ошибкой, её прежние узлы сохраняются (прежнее поведение).
Токены подписок не меняются. Изменился состав хеша клиента (поле `total_bytes`, без счётчиков),
поэтому первая синхронизация после обновления разово пишет по одной записи аудита
`client updated` на каждое наблюдение клиента.

## 16. R46 без принудительной синхронизации и фоновые циклы бота (результаты от 2026-10-05, после приёмки)

Разделы 1–10 не пересматриваются. R46 там доказан сценарием `whitelist_e2e.py`, который перед
каждой проверкой подписки сам вызывал `POST /admin/sync` SubHub и ждал завершения: это
доказывает результат принудительной синхронизации, но не то, что её запускает приложение.
Фоновые циклы `app.main` в той приёмке по расписанию не работали (§9).

**Метод.**
- Отдельный сценарий `ops/acceptance/whitelist_background_e2e.py`, протокол прогонов —
  `docs/acceptance/whitelist_background_e2e_2026-10-05.md`. `whitelist_e2e.py` сохранён как
  сценарий с принудительной синхронизацией.
- После подготовки стенда сценарий `/admin/sync` не вызывает: наблюдатель только читает
  `/admin/clients`, `/admin/subscriptions/resolve`, `/connection/{token}`, `/health`, а запрос к
  `/admin/sync` его HTTP-клиент отклоняет. Исключение — фаза Z в самом конце (проверка D-5);
  после неё проверок R46 нет.
- Фоновые циклы запускает `app.main.start_background_tasks(bot, settings)` — сборка, вынесенная
  из `run()` без изменения состава и условий включения; `run()` вызывает её же рядом с
  Telegram polling. В сценарии polling не запускается, `bot` — записывающая заглушка (нужна
  только уведомлениям об окончании). Работают все четыре цикла: проверка серверов (с
  `recover_confirmed_payments`, отложенными обновлениями и очередью «Обход белых списков»),
  обход сверки расхода, уведомления об окончании, сбор IP. Настройки читает `get_settings()` из
  окружения, как процесс бота; ускорены: `SERVER_HEALTH_POLL_SECONDS=5` (production 60),
  `WHITELIST_RECONCILE_MINUTES=1` (15), `EXPIRY_NOTIFY_POLL_SECONDS=5` (300),
  `SUBHUB_TIMEOUT_SECONDS=5` (15). Обработчики бота вызываются напрямую, как в §6.
- Быстрый триггер и резервный опрос разделены стендом (`stack.sh`): **SubHub-T** — адрес у бота,
  резервный опрос 1 ч, контейнер перезапускается при подготовке (что плановый опрос не попал в
  прогон, проверяется в конце); **SubHub-P** — бот о нём не знает, только опрос 30 с (минимум
  SubHub). Оба читают те же панели и пишут журнал запросов (INFO).
- Доказательство каждого изменения — время появления в SubHub-T и SubHub-P; в журнале SubHub-T
  `POST /admin/sync` с кодом ответа и следующее за ним чтение нужной панели; источник запроса —
  окно обработчика или строка журнала бота `SubHub: запрос синхронизации после фоновых изменений
  (<причина>)`, которую фоновый цикл пишет перед запросом (добавлена этой задачей). Ожидания
  конечны: 30 с для обработчика, 180 с для фона, 60 с «без нового действия», опрос + 30 с для
  SubHub-P.
- Время: истечение — сдвиг `expires_at` в БД и штатная команда `/sync`; «прошло 5 минут» перед
  возобновлением прерванной оплаты — сдвиг `confirmed_at`. Падение процесса между фиксацией
  оплаты и панелью — исключение `BaseException` на первом изменении панели (настоящий updater,
  обёрнутый в сценарии); настоящий процесс не убивался.

**Найденные дефекты и исправления.**

**D-5 (средний, VpnBot). Разрыв соединения SubHub ломал best-effort-триггер.**
`SubHubClient.trigger_sync` и `resolve` превращали в «SubHub недоступен» только таймаут и
сетевые ошибки. `httpx.RemoteProtocolError` («Server disconnected without sending a response») —
так отвечает опубликованный порт контейнера SubHub во время его запуска — выходил из
`trigger_configured_sync` исключением. В `_after_applied_payment` триггер вызывается до
уведомлений: после уже сохранённой оплаты обработчик падал, пользователь не получал сообщение о
продлении, администратор — результат; повторное нажатие отвечало «уже применена», и
уведомление терялось окончательно. То же в trial (пользователь не видел ответа); при
получении ссылки подписки `resolve` бросал то же исключение мимо обработки `SubHubError` (по
коду, обработчик тестом не проверялся). Оплата не терялась и повторно не начислялась. Исправление: `subhub_client.py` ловит `httpx.TransportError`
(таймаут, сеть, протокол) в обоих методах; `trigger_configured_sync` при неудаче пишет
предупреждение `SubHub: синхронизация не запрошена: …` (раньше неудача была не видна).

**D-6 (средний, SubHub). Триггер во время идущей синхронизации терялся.** `POST /admin/sync`
при занятой глобальной блокировке отвечал 409 и ничего не планировал; бот считает 409
успехом. Если идущий проход уже прочитал панель, изменение попадало в подписку только с
резервным опросом (`refresh_interval_seconds`, в примере конфигурации 300 с). На стенде:
медленная обычная панель держит проход, покупка возобновила исчерпанный конфиг, её триггер
получил 409 — конфиг не появился за 60 с. Исправление (`subhub/app/sync.py`, `app/main.py`):
`SyncService.request_sync` — если проход идёт, сразу после него выполняется ещё один полный
проход (запросы за время прохода объединяются в один повтор); эндпоинт отвечает 202
`accepted` или `queued`. Повтор встроен в `sync_all`, поэтому срабатывает и после планового или
стартового прохода. Клиент бота по-прежнему принимает 409 (совместимость с необновлённым SubHub).

**D-7 (низкий, VpnBot). Административные команды не вызывали триггер.** `/extend`, `/sync`,
`/wladjust` и `/wlresolve` меняют панели, но SubHub не уведомляли — изменение (например,
возвращение конфигов после ручного продления истёкшей подписки) ждало опроса. Исправление:
триггер после успешной операции, как в остальных обработчиках (`/sync` — всегда после
переноса срока; остальные — если изменение применено).

**D-8 (низкий, VpnBot). Возобновлённая после рестарта оплата не уведомляла SubHub.**
`_server_health_poller` вызывал `recover_confirmed_payments`, игнорируя число применённых

## 17. Очередь применения не зависит от проверки здоровья серверов (2026-10-06)

Замечание P2 повторного ревью (`docs/REVIEW_2026-10-06.md`): автоматический
`process_due` был внутри `_server_health_poller` и не запускался при
`SERVER_HEALTH_POLL_SECONDS=0`.

**Причина.** Очередь применения была частью цикла проверки серверов, а тот запускался
только при `SERVER_HEALTH_POLL_SECONDS > 0`. Сверка расхода (`_whitelist_reconcile_poller`)
очередь не применяет.

**Исправление.** Отдельный `_whitelist_queue_worker` (`WHITELIST_QUEUE_POLL_SECONDS`),
запускаемый всегда и в единственном экземпляре на процесс; из цикла проверки серверов
вызов убран. Подробности — `WHITELIST_SERVICE.md`, «Worker очереди применения».

**Регрессионные тесты** (`tests/test_whitelist_queue_worker.py`, постоянный набор;
БД — файловая SQLite в WAL с отдельными соединениями у теста и worker'а):

| Сценарий | Проверка |
|---|---|
| Комбинации health `0/60` × сверка `0/15` | worker очереди запущен ровно один раз во всех четырёх; health и сверка — только при значении > 0 |
| Повторный `start_background_tasks` | второго worker'а нет; после `stop` запуск снова возможен |
| Остановка при зависшем запросе к панели | задача отменяется, `stop_background_tasks` завершается |
| Цикл проверки серверов | `process_due` не вызывается (нет двойной обработки) |
| Начисление при недоступной панели → восстановление (health `0` и `60`) | без административной команды квота 10 → 35 ГиБ; одна покупка в журнале, `paid_bytes` = 25 ГиБ; SubHub уведомлён ровно один раз; повторных проходов без изменений |
| Недоступный SubHub | применение не откатывается, повторного применения нет, одна покупка |
| Backoff | при `next_sync_at` в будущем панель не затрагивается; после истечения — применение |
| Сбой цикла (исключение в `process_due`) | worker продолжает опрос |
| Ошибка одного из четырёх аккаунтов | остальные три применены, сбойный остаётся в очереди и повторяется |
| «Рестарт» worker'а | первый worker при недоступной панели ничего не применяет; новый после восстановления применяет ровно один раз |
| Истёкшая подписка с сохранённым платным трафиком | квота 35 ГиБ применена, клиент выключен сроком, `paid_bytes` = 25 ГиБ; продление включает без повторного начисления |

Падение до исправления: тесты восстановления (`health=0`) завершались по таймауту —
квота на панели оставалась 10 ГиБ.

**Проверки.** `tests/test_whitelist_queue_worker.py`, `test_subhub_trigger.py`,
`test_whitelist_reconcile.py` — 48 passed, 3 прогона подряд. Весь набор (SQLite):
551 passed, 10 skipped, 1 failed — `test_whitelist_retarget.py::test_existing_user_moves_to_new_inbound`

Ruff по изменённым файлам — без ошибок; mypy `app/main.py`, `app/config.py` — новых

**Не выполнялось.** Прогон на PostgreSQL; сквозная приёмка

## 18. Сброс счётчика при неопределённом событии (результаты от 2026-10-06, P1 ревью)

Источник — `docs/REVIEW_2026-10-06.md`, раздел Spec. Требование — §4 задания: смена эпохи
счётчика должна обнаруживаться, сброс не должен создавать доступный трафик.

**Причина.** `_settle_reading` завершалась при наличии `uncertain` события до проверки
уменьшения счётчика и смены `traffic_row_id`. Точка, строка статистики и прочитанное значение
в этом состоянии не обновлялись, поэтому после `resetTraffic` абсолютная квота оставалась
`старая точка + остатки`. `resolve_uncertain` ставил точкой верхнюю границу периода
прежней эпохи и сравнивал её со счётчиком новой.

**Воспроизведение** (`MockPanelUpdater`, SQLite; тест
`test_reset_with_uncertain_event_does_not_grow_available_volume`): точка 100 ГиБ,
остатки 2 + 15; продление при недоступной статистике; 5 ГиБ расхода → `uncertain`;
квота 125, счётчик 105, доступно 20. После `resetTraffic` и `sync_user` до исправления:
квота 125, счётчик 0, клиент включён, конфликта нет — **доступно 125 ГиБ**.

**Исправление.**

- Эпоха проверяется при каждом чтении до обработки событий. Сравнение — с последним
  прочитанным значением `usage_observed_bytes` (миграция `f3a4b5c6d7e8`), которое
  обновляется и в состоянии `uncertain`; для строк до миграции — с наибольшим из точки и
  границ/привязок событий. Пересоздание обнаруживается по `traffic_row_id`.
- Новая эпоха продолжает последнее чтение прежней `L`: точка и привязки неприменённых
  событий уменьшаются на `L`. Расход прежней эпохи, ещё не списанный с остатков, остаётся
  вычтенным из квоты (отрицательная точка). Остатки, начисления и журнал не меняются;
  пишутся `conflict` и `usage_rebase`.
- Варианты `/wlresolve` после сброса считаются по прочитанному периоду прежней эпохи;
  после решения списывается весь последующий расход, включая расход новой эпохи.
  `/wladjust` задаёт остатки на текущий счётчик.
- Утрата счётчика (замена сервера, удаление клиента) снимает у неприменённых событий
  привязки и верхнюю границу прочитанного периода: они несравнимы со счётчиком нового
  клиента. Решение — только `/wladjust`, как было задокументировано.
- Пакетное чтение, начатое раньше сохранённого чтения учёта, не применяется:
  `usage_observed_at` — момент не раньше фактического чтения, сверка возвращает BUSY.
- Карточка `/wl` показывает последнее чтение, не списанный расход прежней эпохи и
  пометку, что вариант решения относится к периоду до сброса.

**Ограничения.**

- Расход между последним чтением и сбросом неизвестен и не списывается (как и прежде);

  дополнительно объём, равный этому значению.

- Замена сервера при неразрешённом событии не переносит прочитанный на прежнем счётчике

- Реальная 3x-ui, Telegram, Happ и production не использовались; поведение панели —
  модель `MockPanelUpdater` (`resetTraffic` обнуляет счётчик и включает клиента,

## 19. Перенос клиентов при смене целевого inbound (2026-10-06, P1 ревью)

Источник — `docs/REVIEW_2026-10-06.md`, «смена целевого inbound не переносит существующих
пользователей». Модель и регламент — `WHITELIST_SERVICE.md`, «Смена целевого inbound и
перенос клиентов» и §6 шаг 10.

**Причина.** Очередь выбирала только `desired_version > applied_version`, а смена цели
(`choose_inbound`, сверка реестра, команды) учёты не меняла; размещение клиента нигде
не хранилось и фоновой сверкой не сравнивалось. `apply_quota_client` лишь дополнял
привязки текущей целью и flow (заданный flow панели не менялся). Итог: сервер «готов»,
применено 0 учётов, клиент на прежнем inbound.

**Контракт 3x-ui** (исходники тегов v3.2.0, v3.3.0, v3.4.0, v3.5.0, v3.6.0, v3.7.0, v3.8.0,
v3.9.0): `POST clients/{email}/attach` и `/detach` с `{"inboundIds": [...]}` есть во всех;
attach копирует общую запись и не пересоздаёт строку статистики; detach снимает только
существующие привязки с `keepTraffic=true`; фильтр `clients/update?inboundIds=` — с 3.3.0
(3.2.0 пишет тело с flow во все привязки); flow — по привязке (`settings.clients[]`,
`client_inbounds.flow_override`); в 3.9.0 detach включённого клиента при
`restartXrayOnClientDisable=true` ставит перезапуск Xray (D-3), в 3.2–3.8 — только при
сбое API Xray.

**Исправление (модель восстановления).**

- Подтверждённое размещение `whitelist_accounts.placement_*` и привязки, созданные
  услугой, `whitelist_placements` (миграция `a4b5c6d7e8f9`). Очередь выбирает учёты, чьё
  подтверждённое размещение не совпадает с текущей целью/flow из БД, — смена любым
  путём находится без отдельной пометки и после рестарта; backoff соблюдается.
- Порядок: чтение → намерение `attaching` (commit) → attach → update прочих привязок с их
  flow → update цели с явным flow → проверка (квота, срок, enable, привязка, flow в
  `inbounds/get`) → `detaching` (commit) → detach → проверка → `placement_*`.
- Принадлежность: строка услуги создаётся только после чтения, показавшего отсутствие
  привязки (или вызовом, который сам прочитал и прикрепил). Без строки — чужая
  привязка: не снимается. Учёты до миграции своей прежнюю привязку не объявляют;
  `/wlclaim` — решение администратора (в аудите).
- Чтение после detach сверяет счётчик: пересоздание строки статистики — новая эпоха,
  квота пересчитывается (доступный объём не растёт).
- Фоновая сверка сравнивает размещение (целевая привязка, flow цели, прежние привязки
  услуги) и снимает подтверждение без сброса backoff.
- `/addinbound`, `/delinbound`, `/clearinbounds` на whitelist-сервере снимают готовность
  до синхронизации (новая цель/flow проверяются на совместимость с SubHub до переноса).
- Админка: «Размещение на inbound N (flow): подтверждено X из Y; ожидает Z; ошибка E» и
  напоминание, что готовность сервера — не перенос; `/wl` — размещение и привязки; SubHub
  уведомляется после порции очереди при выборе цели/синхронизации и worker'ом.
  `ops/whitelist_check.py`: `placement_mismatch`, `placement_pending`.

**Регрессионные проверки** (постоянный набор; модель панели `MockPanelUpdater` с
семантикой attach/detach/фильтра update/flow по привязке и статистики, сверенной с
исходниками; проверяются фактические привязки, flow, квота и доступный объём на модели
панели).
