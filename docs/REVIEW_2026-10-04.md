# Ревью VpnBot — 4 октября 2026

## Результат

**Обновление после согласия владельца:** новая версия внедрена в production; адресный инцидент исправлен. Текущий статус и ограничения описаны в [DEPLOYMENT_2026-10-04.md](DEPLOYMENT_2026-10-04.md). Остальной текст ревью фиксирует исходное состояние.

Причины двух заявленных проблем установлены по коду и чтению production:

1. Бот отправляет в панели устаревшие inbound ID. На сервере 1 удалены `22`, `23`, `24`, на сервере 3 — `9`, но в БД бота эти цели включены. Новые `27`, `30`, `31` сервера 1 отсутствуют в локальном реестре бота.
2. Telegram ID сохраняется в `users`, но при создании глобального клиента панели код всегда отправляет `tgId=0`. У клиента из примера это подтверждено на всех семи панелях.

Локально подготовлены исправления и регрессионные тесты. На production изменения кода, БД, конфигурации, подписок, inbound'ов и контейнеров не применялись. Авторизация при чтении API панелей создаёт обычные сессии и записи в их журналах.

Полностью исправленным production пока считать нельзя: требуется отдельное применение проверенных изменений и сверка данных. Ниже разделены подтверждённые инциденты, исправления, решения по безопасности и оставшиеся риски.

## Разбор PAY-1C3F1344

Заявка создана/применена 2 октября 2026 в 11:19:05 МСК на 180 дней. Целевой срок — 31 марта 2027 в 11:19:05 МСК.

На первой попытке серверы 1 и 3 отвергли создание клиента из-за несуществующих inbound. При этом исходный billing записал оплату как `APPLIED` и выдал «Доступ продлён», поместив два отказа в очередь.

Позднее очередь завершила обе записи за пять попыток, к 11:23:19 МСК. При диагностике:

- заявка `APPLIED`, её `last_error` очищен;
- клиент активен в БД и существует на всех семи панелях;
- срок на панелях соответствует целевому с расхождением менее секунды на сервере 1;
- на сервере 1 клиент привязан к `1,9,19,27,30,31`, хотя в конфигурации бота включён ещё `26`, а новые `27,30,31` в ней отсутствуют;
- на сервере 3 клиент привязан к `1,5,8`, удалённый `9` отсутствует;
- `tgId` равен нулю на всех семи панелях, хотя Telegram ID пользователя в БД бота корректный.

Следовательно, исходное сообщение описывает реальный временный отказ. Последующий успех очереди подтверждает обновление срока, но сам по себе не доказывает правильность всех подключений и полей клиента.

Бот создаёт клиентов и привязки к существующим inbound'ам. Создание самих сетевых inbound'ов на 3x-ui не входит в реализованный provisioning. `/importinbounds` считывает уже созданные на панели inbound'ы.

## Оставшиеся риски и решения

### P1 — административные права зависят от тарифа

`app/services/access.py:resolve_effective_role` выдаёт `ADMIN`, если Telegram ID явно разрешён **или** у пользователя бессрочная подписка с mapping. `SessionMiddleware` пересчитывает и сохраняет эту роль при каждом событии. Фильтры административных обработчиков доверяют роли.

Это существующее правило прямо закреплено исходными тестами. Оно не было молча изменено: задан вопрос владельцу проекта. Рекомендация — только явный список `ADMIN_TELEGRAM_IDS`; перед rollout проверить и включить всех легитимных администраторов. На production в настройке указан один ID, а вне неё имеются три пользователя с бессрочными VPN-клиентами. Само наличие бессрочного клиента ещё не заменяет проверку mapping для каждого из них.

### P1 — пароли панелей не защищены шифрованием приложения

`SECRET_KEY` не настроен в работающем боте. `app/crypto.py` в этом режиме сохраняет пароль как есть; чтение всех серверов без ключа успешно. Все панели используют HTTPS, но копия БД/дамп остаётся чувствительным материалом.

Нужны: резервная копия с ограниченным доступом; генерация и отдельное безопасное хранение постоянного ключа; настройка ключа; контролируемая перезапись существующих паролей через `EncryptedString`; проверка чтения всех семи панелей. Простое добавление переменной не перешифрует существующие строки. Ключ после миграции нельзя менять без процедуры перешифрования.

### P1 — биллинг и панели не образуют одну транзакцию

Сохранение target до HTTP-запросов правильно защищает повтор одной заявки от повторного начисления. Однако row lock заявки освобождается на commit перед панелями. Разные заявки одного пользователя не сериализуются по общему состоянию VPN-клиента, очередь не имеет полноценного claim/lease, а `CONFIRMED` не входит в `latest_open_for_user`.

Риск: пересечение отдельной оплаты, retry и фоновой очереди может перезаписать более новое состояние. SQLite-тесты не доказывают корректность PostgreSQL `FOR UPDATE`. Следующий необходимый этап — тест конкуренции на PostgreSQL и durable outbox/версия желаемого состояния клиента с сериализацией обработки. Локальные исправления очереди закрывают последовательные сбои, но не заявляются как полное решение конкурентных сценариев.

### P1/P2 — частичный успех внешней операции требует сверки

Панель может создать клиента до возврата ошибки привязки. В исходном состоянии это наблюдалось в цепочке создания/повтора, но точный порядок внутренних изменений каждой панели из логов бота не доказан. Предварительная проверка целей уменьшает риск, а retry умеет переиспользовать клиента. После timeout результат всё равно следует перечитать; нельзя считать timeout гарантией отсутствия mutation.

Для legacy API отдельная mapping только на primary inbound не описывает всех фактически созданных клиентов. Удаление подписки на старых панелях требует дополнительной проверки всех inbound. На просмотренных production панелях используется новый API; legacy deletion в этой проверке с реальной панелью не воспроизводился.

### P2 — старые ошибки оплат без ожидающих задач

В production есть `APPLIED` с непустым `last_error` и нулём pending-записей:

- `PAY-3B28A2AB` — 20 августа;
- `PAY-58610945` — 21 августа;
- `PAY-37381219` — 21 августа.

Нельзя просто стереть ошибки: сначала сравнить сохранённый срок и реальные подключения каждого клиента, затем выполнить адресную синхронизацию и зафиксировать результат. При проверке заявок, зависших в `CONFIRMED`, не было.

### P2 — мониторинг и производительность

Health-check проверяет login, поэтому «online» не гарантирует правильные inbound/протоколы/выдачу подписки. Антишеринг создаёт отдельную API-сессию для каждой mapping; с ростом клиентов растут число логинов, задержка обхода и объём логов. Нужны отдельные метрики очереди и возраста незавершённых операций, контроль расхождений реестра и переиспользование сессии на сервер в пределах обхода.

### P2 — эксплуатация и воспроизводимость

- Свободно 1,2 ГБ на корневом разделе. До сборки/пересоздания контейнеров нужна безопасная проверка занимающих место каталогов. БД/логи/дампы не удалялись.
- `networking.service` и `ifup@eth0.service` находятся в failed, при этом SSH и API работают. Это не доказательство причины ошибок панелей. Проверять схему управления сетью следует с доступной консолью провайдера, без слепого рестарта сети.
- Найдены ручные dump-файлы. Регулярное внешнее резервирование и успешное тестовое восстановление по доступным данным не подтверждены. Утверждения «бэкапов нет» нет.
- Production содержит untracked override и резервные `.py.bak`; перед rollout учесть override и сохранить действующий image/config. Не выполнять `git clean` в production.
- Зависимости Python имеют широкие диапазоны, lock-файла для воспроизводимого production build нет. Нужен фиксированный набор runtime-зависимостей с контролируемыми обновлениями.
- До изменений mypy сообщает 80 ошибок типов. Это отдельный долг, преимущественно Optional в aiogram-обработчиках; зелёный pytest его не отменяет.
- `VPNSite/` уже находился в рабочем дереве как untracked до начала ревью. Для воспроизводимости сайта необходимо отдельно включить предназначенные исходники в Git, без локальных env/node_modules/dist.

## Порядок применения в production

1. Согласовать правило администраторов; инвентаризировать действующий override, сохранить рабочий image и конфигурацию; создать и проверить резервную копию БД. Отдельно подготовить миграцию паролей с `SECRET_KEY`.
2. Убедиться в достаточном свободном месте. Применить локальные правки в согласованное окно. Не запускать одновременно два polling-процесса с одним BOT_TOKEN.
3. Уже на новой версии выполнить `/importinbounds 1` и `/importinbounds 3`. На старой версии эта команда не отключает удалённые цели, поэтому одного старого импорта недостаточно. Проверить итоговый список и вручную подтвердить назначение новых inbound.
4. Для конкретного клиента выполнить `/provision <его Telegram ID>` с сохранённым сроком. В новой версии это переносит Telegram ID и разрешённый состав подключений. Повторная оплата не нужна. Бессрочная подписка должна остаться бессрочной.
5. Повторить адресную сверку клиента: `tgId` совпадает с владельцем, срок не уменьшен, configured/live/client inbound согласованы. Затем проверить тестовым подключением нужные протоколы/транспорты и импорт через SubHub/Happ.
6. Разобрать три старых `APPLIED + last_error` отдельно. Прерванные `CONFIRMED` с target можно возобновить `/confirm <код>`, не меняя target вручную.
